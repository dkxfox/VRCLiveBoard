# 11 · 事件 → 聊天框(步 6)

> 这一层的职责: **事件 → 什么时候推哪条文本**。离线纯逻辑 + 两个注入端口, 所以不需要凭据、不联网就能全测。
> 代码: `lib/bridge.js`(+ `lib/bridge.test.js`, 48 条断言)。

## 一条弹幕的旅程
```
wss 帧(op=5) → frame.js 解帧 → session.js onEvent(JSON)
   → events.js normalize()  → 统一事件 {kind, cmd, uname, text, …}
   → bridge.js  handleRaw() → 文案 / 屏蔽词 / 截断 / 聚合 / 抢占判定 / 排队
   → push(text, priority, ttlMs, force)  → 也就是 composer.pushTransient(...)
   → composer.tick() 每秒按优先级挑一条 → OSC 聊天框
```
桥的两个端口(插件 `index.js` 负责接上):
| 端口 | 接什么 |
| --- | --- |
| `push(text, priority, ttlMs, force)` | `ctx.chatbox.send(text, {priority, ttlMs, force})` |
| `current()` | `composer.current`(当前屏幕上是哪条、什么优先级、什么来源) |

## 配置(都可改, 设置面板见步 7)
| 键 | 默认 | 说明 |
| --- | --- | --- |
| `prefix` | `''` | 统一前缀, 如 `[弹幕] ` |
| `showUname` / `unameSep` | `true` / `': '` | 弹幕是否带昵称 |
| `maxLen` | `100` | 截断长度(composer 自己还有 144 上限) |
| `throttleMs` | `1500` | 两条之间的最小间隔(自我保护, 防刷屏喂 OSC) |
| `ttlMs` / `highValueTtlMs` | `8000` / `15000` | 普通 / 高价值 显示时长 |
| `forceHighValue` | `true` | 高价值用 `force` 推(绕过 composer 自身发送间隔; 我们已自节流) |
| `blockedWords` / `maskWith` | `[]` / `'***'` | 屏蔽词替换; **整条都是屏蔽词就直接丢弃** |
| `kinds` | 弹幕/礼物/SC/上舰 = 开 | 进房/互动/点赞/状态类默认关 |
| `aggregateKinds` | `['DANMAKU']` | 哪些类别做重复聚合 |
| `basePriority` | `75` | 插件卡片里那个"优先级"= **基数**; 各类型按 policy 默认值相对偏移(弹幕 +0 / 互动 −5 / 礼物 +5 / SC +13 / 上舰 +17) |
| `sourcePriority` | `{}` | 逐类绝对覆盖(优先于基数) |
| 其余 | 见 `policy.js` | `preemptBackground` / `respectPriority` / `protectSources` / `queueMax` / `highValueQueueMax` / `danmakuQueueTtlMs` / `aggregateWindowMs` / `aggregateFormat` |

## 处置规则(一张表)
| 情况 | 结果 |
| --- | --- |
| 屏幕空 / 当前是我们自己刚推的那条 | 直接显示(仍受节流限制) |
| 当前是 `livetranslate` / `ocrregion`(来源保护) | **排队**(手动触发、需要连读的功能不许被打断) |
| 当前显示优先级 ≥ `respectPriority`(85) | **排队**(硬规则: 手动结果优先; 想抢就调低它) |
| `preemptBackground=false` | **排队**(连公告板也不抢) |
| 我方优先级 > 当前 | **抢占**显示 |
| 优先级不高于当前 / 距上一条不足 `throttleMs` | **排队**, 每秒 tick 时再试 |
| 排队超时(弹幕 30s) | 丢弃并**记日志**(丢弃必须可见) |
| 队列超上限(普通 20 / 高价值 50) | 丢最旧并**记日志** |
| SC / 礼物 / 上舰 | 永不因超时丢; `dequeue` 出队时**先高价值后普通**(各自 FIFO) |
| 重复弹幕(同一句, 5 秒窗口) | 首次原样显示 → 窗口内压住 → 窗口结束补 `666×3` |

## 两条踩过才写下来的规则
1. **自己刚发的那条不算挡自己**(否则弹幕会饿死): `composer.current` 只在真的发出时更新, 而且过期不自动清空; 若把它当成"别人占着屏", 后来的弹幕会因为"优先级不高于它"永远排队。判定: `current.sourceId==='transient' && current.text === 我们最后推的文本`。
2. **聚合窗口的键是弹幕原文, 不是最终文案**: 默认文案是"昵称: 文本", 拿它当键的话"很多人同时刷 666"永远聚不起来(每个人昵称都不同)。所以键取 `ev.text`, 补的计数行是 `666×3`(不加昵称)。

## 已知限制(诚实)
- 聚合是"首次原文 + 窗口结束补计数"两条, **不是实时跳数**(composer 没有"改已压入文本"的 API, 见条目 192);
- 队列只在内存, 插件停用/程序重启即丢(与"不采集不落库"口径一致);
- 一条消息推上去后, 到它显示为止还有 composer 自身 ≤1 秒的 tick 延迟与 1.2 秒的发送间隔 —— 我们的节流是在此之上的;
- 屏蔽词是**插件自己**的一份词表, 与程序内置的 `swearfilter` 相互独立(两层都会生效, 不冲突)。
