# 07 · 接入实现要点(拿到凭据后先读这份)

> 整理于 2026-09-20。内容来自**跑通的官方接入实现**(blivedm 的 `open_live.py`)与官方文档标题, 逐条核对过。
> ⚠️ 协议与字段可能变 —— 真连之前再复核一次 [官方接入文档](https://open-live.bilibili.com/document/)。

## 一、需要四个参数(不是两个!)
| 参数 | 含义 | 来源 |
| --- | --- | --- |
| `access_key_id` | 开放平台凭据 ID | **申请通过邮件**(已拿到) |
| `access_key_secret` | 开放平台凭据密钥(签名用) | **申请通过邮件**(已拿到) |
| `app_id` | **项目 ID**(数字) | 开放平台后台**创建一个项目**后得到 |
| `room_owner_auth_code` | **主播身份码** | 主播在开放平台授权/绑定直播间后生成 |

## 二、三个端点
```
POST https://live-open.biliapi.com/v2/app/start      # 开始: 传 app_id + code(主播身份码) → 拿长连接与认证
POST https://live-open.biliapi.com/v2/app/heartbeat  # 项目心跳(20 秒一次)
POST https://live-open.biliapi.com/v2/app/end        # 结束场次
```
`start` 成功后会拿到这些(名称以官方返回为准):
- `game_id`: **项目场次 ID**(后续心跳/结束都要带);
- `host_server_url_list`: **弹幕服务器地址列表**;
- `auth_body`: **连接弹幕服务器用的认证包内容**(直接塞进 WebSocket 认证帧);
- `room_owner_uid` / `room_owner_open_id`: 主播标识。

## 三、签名规范(照抄即可)
请求头(顺序即签名串顺序, **不能重排**):
```
x-bili-accesskeyid:      <access_key_id>
x-bili-content-md5:      <请求体的 MD5(hex) —— 对 JSON(body) 的 UTF-8 字节>
x-bili-signature-method: HMAC-SHA256
x-bili-signature-nonce:  <随机串(uuid 去掉横线即可)>
x-bili-signature-version:1.0
x-bili-timestamp:        <秒级时间戳>
```
**签名串** = 上面六行按此顺序用 `key:value` 拼接、行间 `\n` 连接(不含末尾换行);
**签名** = `HMAC-SHA256(key = access_key_secret, msg = 签名串)` 的 hex;
**放到** `Authorization: <签名>`;同时带 `Content-Type: application/json` 与 `Accept: application/json`。

等价 Node 实现(Node 内置 `crypto`, 零依赖):
```js
const crypto = require('crypto');
function signHeaders(accessKeyId, accessKeySecret, bodyStr) {
  const h = {
    'x-bili-accesskeyid': accessKeyId,
    'x-bili-content-md5': crypto.createHash('md5').update(Buffer.from(bodyStr, 'utf8')).digest('hex'),
    'x-bili-signature-method': 'HMAC-SHA256',
    'x-bili-signature-nonce': crypto.randomUUID().replace(/-/g, ''),
    'x-bili-signature-version': '1.0',
    'x-bili-timestamp': String(Math.floor(Date.now() / 1000))
  };
  const strToSign = Object.keys(h).map((k) => k + ':' + h[k]).join('\n');
  return Object.assign({
    Authorization: crypto.createHmac('sha256', accessKeySecret).update(strToSign, 'utf8').digest('hex'),
    'Content-Type': 'application/json',
    Accept: 'application/json'
  }, h);
}
```

## 四、完整时序
```
1. start(app_id, code)  →  拿 host_server_url_list + auth_body + game_id
2. 连 wss(从 host_server_url_list 选一个) → 发认证帧(auth_body) → 等认证回应
3. 双心跳(两个都要):
   · 连接心跳: 每 30 秒发一次 WebSocket 心跳帧(op=2)
   · 项目心跳: 每 20 秒 POST 一次 /v2/app/heartbeat(带 game_id)
4. 收消息帧(op=5) → 解 protover(2=zlib / 3=brotli) → JSON → 按 CMD 分发
5. 退出/停止时: POST /v2/app/end(带 game_id), 再关 WebSocket
```
⚠️ 心跳漏发会掉线; 断线要**指数退避**重连; 风控错误码要识别并退让(别死循环)。

## 五之二、开放平台的消息长什么样(2026-09-20 查实, 接真环境前必读)

来源: blivedm 的 `handlers.py` 的 `_CMD_CALLBACK_DICT` 与 `models/open_live.py`(与官方文档同构的成熟实现), blivechat 的 `services/chat.py`(面板/弹幕应用)。

**① CMD 名和网页协议不是一套**(这点最坑): 官方开放平台自成一套前缀, 认错名字会导致"连上了但一条都不显示":

| 开放平台 CMD | 含义 |
| --- | --- |
| `LIVE_OPEN_PLATFORM_DM` | 弹幕 |
| `LIVE_OPEN_PLATFORM_DM_MIRROR` | 跨房弹幕(可能缺字段) |
| `LIVE_OPEN_PLATFORM_SEND_GIFT` | 礼物 |
| `LIVE_OPEN_PLATFORM_GUARD` | 上舰 |
| `LIVE_OPEN_PLATFORM_SUPER_CHAT` / `..._SUPER_CHAT_DEL` | 醒目留言 / 撤回(**是 _DEL, 不是 _DELETE**) |
| `LIVE_OPEN_PLATFORM_LIKE` | 点赞 |
| `LIVE_OPEN_PLATFORM_LIVE_ROOM_ENTER` | 进房 |
| `LIVE_OPEN_PLATFORM_LIVE_START` / `..._LIVE_END` | 开播 / 下播 |
| `LIVE_OPEN_PLATFORM_INTERACTION_END` | **服务器主动停止推送**(常见于心跳超时)→ 必须重新 start |

**② 载荷字段是平铺 snake_case, 与网页的 `info[]` 完全不同**: 弹幕用 `msg`(不是 info[1])、`uname`、**`open_id`(没有 uid)**、`guard_level`、`fans_medal_name/level`、`dm_type`(1=表情弹幕, 只有 `emoji_img_url` 没有文字)、`reply_uname`(回复某人); 礼物 `gift_name`/`gift_num`/`price`/`paid`/`combo_gift`; 上舰 `user_info.uname`/`guard_num`/`guard_unit`(可能是 `*3天`); SC 金额字段叫 **`rmb`**, 时长由 `start_time`/`end_time` 算。

**③ 主播自己的弹幕会推回来**(用户问的): blivechat 的开放平台弹幕处理里明确写着 `if message.open_id == client.room_owner_open_id: author_type = 3  # 主播` —— 也就是说**默认会传回**, 靠 `open_id` 与 start 返回的 `anchor_info.open_id` 比对来认人(网页协议那边才是比 `uid == room_owner_uid`)。插件因此默认**不转发主播自己的消息**(`ignoreSelf`, 可关), 并给一次性提示, 免得用户以为插件坏了。

**④ 主播信息在 `data.anchor_info` 里**(`uid`/`open_id`/`room_id`/`uname`/`uface`), 不是顶层的 `room_owner_*`(老写法两个都认)。

**⑤ 压缩**: 开放平台会用 **zlib(deflate)**, 网页端已不用; 帧解析两种都要支持(我们的 `frame.js` 都支持)。

**⑥ 实机联调踩到的三个坑(2026-09-25)**

1. **`start` 的真实响应是嵌套的**: `data.game_info.game_id` + `data.websocket_info.{wss_link[], auth_body}` + `data.anchor_info.*`。
   文档正文里那几个扁平字段名(game_id / host_server_url_list / auth_body)只是"字段清单", 实际包在 game_info / websocket_info 里 —— 按扁平解析会**全部取空**。
2. **`end` 的请求体是 `{app_id, game_id}`**(不是心跳体 `{game_id}`); 心跳体只带 game_id。两者不能混用。
   另外 **7000 / 7003 = "项目已关闭"**, 应当按成功处理(end 时项目已经关了不算失败)。
3. **没拿到 game_id 时千万不要"照发"**: 平台会回"缺少 game_id", 而且**每次 start 都会在平台侧留下一个场次** ——
   连着试几次就会撞 **7010「插件或直播工具同一房间启动数量超过配置上限」**, 看起来像"平台限制", 其实是自己没关干净。
   正确做法: 结束后一定要 end; 没有场次号就跳过 end; 撞上 7010 时等平台按心跳超时释放(几分钟)或重启直播。

## 六、凭据怎么放(安全设计, 开工前定死)
1. **绝不进仓库**: 密钥只存本地 `config.json` 的插件设置段(`config.json` 已 gitignore + 已进打包排除清单);
2. **绝不进日志**: 打日志只允许出现 `access_key_id` 的前 4 位(如 `ak_ab…`), `..._secret` 永远不打印;
3. **界面掩码**: 设置页用 `type="password"` + 只显示尾 4 位; 复制到剪贴板不做;
4. **泄漏就换**: 如果密钥进过截图/聊天记录/公开仓库 → 立刻到开放平台重置;
5. **权限最小**: 这个插件只需要网络访问三个域名, 不声明文件写入与进程权限(见 `manifest.json`)。
