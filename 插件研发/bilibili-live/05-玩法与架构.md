# 05 · 玩法与架构(回来开发时先读这份)

## 六个玩法(按"实现成本/效果"排序建议)
1. **弹幕上头顶**(几乎零成本): `DANMU_MSG` → 现有 `/v1/chatbox` 或 `composer.pushTransient`, 复用现成通道;
2. **礼物触发动作**: `SEND_GIFT` → OSC 参数(换装/特效/表情/道具), 配一张"礼物 → 动作"映射表;
3. **上舰专属播报**: `GUARD_BUY` → 聊天框高亮 + 公告板显示"今日舰长";
4. **弹幕指令**: `!换歌` / `!切页` / `!投票` → 走现有插件 API(`plugCall` 那一套);
5. **互动计分板**: 弹幕投票 / 礼物排名 → 用公告板页面变量刷在头顶(观众实时看到进度 = 互动游戏的核心反馈);
6. **SC 醒目展示**: `SUPER_CHAT_MESSAGE` → 按 `price` 决定展示时长与优先级(项目已有 优先级 + TTL 机制, 天然契合)。

## 架构: 共享上层, 隔离下层
```
玩法层(公告板变量 / 播报 / OSC 动作 / 计分板)          ← 只写一遍
        ↑  BilibiliEvent { type, user, text, value, ts }
传输层 ├─ official adapter   ← 进包(合规): /v2/app/start + heartbeat + Hmac-SHA256 + wss
       └─ dev adapter        ← 只在你本机: 社区协议(不进包, pack-exclude 排除)
```
- 上层只认 `BilibiliEvent` → **同一套玩法代码, 两条路都能跑**;
- 换传输不动玩法; 将来官方扩能力也只改 adapter。

## 体积与依赖(结论)
| 项 | 结论 |
| --- | --- |
| 代码量 | 传输层(帧/心跳/重连) + 官方通道(start/heartbeat/end + 签名) + 事件归一化 + 设置 UI ≈ **600~900 行** |
| 体积 | **30~50 KB**(对比: Lite 包 8.3MB / 自包含 215MB → 约 0.6%, 噪声级) |
| 依赖 | **零新增** —— Node 内置 `WebSocket`(项目里歌词插件已在用)、`zlib`(含 brotli)、`crypto`(Hmac)、`fetch` |
| 不建议 | 引入 `blive-message-listener` 这类库: 会带进依赖树, 还要同步动依赖基线与审计; 自己实现更小更可控 |

## 与现有代码的结合点
- 播报: `composer.pushTransient(text, priority, ttl)` —— 项目已有优先级/TTL 机制;
- 公告板: 新增变量(如 `{bili_online}` `{bili_watched}` `{bili_gift}`), 走现有变量替换体系;
- OSC: 复用现有 OSC 发送通道(礼物 → 参数);
- 授权: `permissions.network` 声明域名 → 走既有**授权红窗**与哈希复核(和官方插件一致);
- 设置页: 参考现有插件设置面板写法(`__plgset_<id>` 那套)。

## 已知工程坑
- `package.json` 的 `engines.node >= 18` 与"全局 `WebSocket` 需 Node 21+/22"不一致 → 建议提到 `>=22`;
- 心跳漏发会掉线; 重连要指数退避; 风控错误码(`-352` 等)要识别并退让;
- 长连接是常驻资源: 插件 `onUnload` 必须关闭(项目对"定时器/连接/监听器必须可停用"有明确要求)。
