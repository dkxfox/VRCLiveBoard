# 03 · 数据指标: 人气 / 看过 / 在线, 到底能查到什么

## 先把三个被混着展示的数字分开
| 指标 | 是什么 | 可信度 |
| --- | --- | --- |
| `online`(房间信息里的"观看人数") | 前端显示的**人气值** | ✗ **算法值** —— B 站专利文件写明: 人气是结合在线人数与主播信息推算的(CN106713938A) |
| `watched_show` / `WATCHED_CHANGE` | **看过人数**(本场累计) | ✓ 相对可信 |
| `ONLINE_RANK_*` | **高能榜/在线榜** | ✓ 常被当作在线的近似 |
| `MaxOnline` | **本场最大在线** | ✓ 但**只有主播自己**能看; 官方文档标注"需要验证" |

**真·实时同时在线人数, 公开接口拿不到。**

## ① 任意直播间(免登录, HTTP)
```
GET https://api.live.bilibili.com/room/v1/Room/get_info?room_id=<长号或短号>
```
| 字段 | 含义 |
| --- | --- |
| `online` | 人气/观看人数(见上表说明) |
| `attention` | 关注数 |
| `live_status` | 0=未开播 / 1=直播中 / 2=轮播中 |
| `live_time` | 开播时间 |
| `title` / `area_name` | 标题 / 分区 |
| `room_id` / `short_id` | 长号 / 短号 |

## ② 主播自己的本场数据(需登录 Cookie `SESSDATA`, 只能查自己)
```
GET https://api.live.bilibili.com/xlive/app-blink/v1/live/StopLiveData?live_key=<场次key>
```
| 字段 | 含义 |
| --- | --- |
| `LiveTime` | 本场时长(秒) |
| `MaxOnline` | 本场最大在线 |
| `WatchedCount` | 本场看过人数 |
| `DanmuNum` | 本场弹幕条数 |
| `AddFans` / `NewFansClub` | 新增粉丝 / 新增粉丝勋章 |
| `HamsterRmb` | 本场收益 |

坑: `live_key` 是**开播场次**的 key, 不提供就是无效数据; 最好下播后立刻拉一次。

```
GET https://api.live.bilibili.com/xlive/app-blink/v1/date/Overview
```
→ 主播端"直播表现"雷达图: 收益 / 累计观看 / 新增粉丝 / 平均观看时长 / 开播时长 / 弹幕数量,
  每个指标还带 "同水平主播" 对比值(`aver`)与量程(`max`)。

## ③ 实时推送(如果走长连接, 这些不用轮询)
- `ROOM_REAL_TIME_MESSAGE_UPDATE`: 粉丝数、点赞等房间实时变化
- `WATCHED_CHANGE`: 看过人数变化
- `ONLINE_RANK_COUNT` / `ONLINE_RANK_V2`: 高能榜/在线榜人数与排行
- `LIKE_INFO_V3_*`: 点赞数变化
- 心跳回应里也带人气值(社区协议 op=3)

## ④ 官方开放平台是否提供这些
**未确认** —— 官方文档站是 JS 渲染, 抓不到正文。申请时按 `01` 的"待确认三问"问清楚;
如果官方不给, 建议**接受少这几个指标**, 而不要用社区接口去补(那等于把风险装回产品)。

## 工程建议
- 免登录房间信息接口轮询 **10~30 秒**一次足够, 再密容易吃风控;
- 展示口径写清楚是"人气"而不是"在线人数"(两者差距可能很大);
- 需要 Cookie 的接口 = 用主播自己的账号查自己的数据, 属于正常用途; 产品里**不要**引导用户填账号密码。
