# 故障经验总结(2026-09-11 审计收尾轮)

> 来源: 本轮"实机测试 → 用户反馈 → 修复"过程中反复出现的同类故障。每条都给**现象 / 根因 / 现已加的护栏**,
> 便于以后遇到相似症状时先查这里, 而不是重新踩一遍。
> 配套: `docs/AUDIT-20260911-01..04`(四份审计行动版)、`docs/DEV-NOTES.md` 140~158 条(逐条修复记录)。

## 一、"假成功": 失败被当成成功(本轮出现 4 次, 危害最大)

| 案例 | 现象 | 根因 | 现在怎么防 |
| --- | --- | --- | --- |
| 截图失败 → 复用旧截图 | 截图失败时聊天框显示**上一轮**截图的译文, 用户无感 | 客户端只认两个已知失败串, 其它一律当成功; 临时文件固定路径且不删 | `checkCaptureReply()` 白名单(只有 `OK` 算成功) + 唯一临时文件 + 用完即删; 门禁 6 条失败用例 |
| 提示音无声却回 OK | 倒计时 5 声全无 | 宿主 beep 读了不存在的变量(`$x0/$y0` → 0/0), 且 `catch {}` 后无条件 `return 'OK'` → 我写的降级路径从未触发 | 失败回 `CAPTURE-FAIL: beep <原因>`; 客户端只要回复不是 `OK` 也降级 |
| 无控制台却回 ok | 命令行窗口开关双向无效, 且显示"已保存" | 父进程没有控制台时子进程**新建**自己的控制台, 对它 ShowWindow 无意义却成功 | 用 `GetConsoleProcessList` 校验父进程在不在这个控制台里, 不在就明确回报不适用 |
| 开关从未生效(长期) | 命令行窗口开关"设置无效, 关掉开不回来" | `GetConsoleWindow` 写在 user32(**实际在 kernel32**)→ 抛 `EntryPointNotFoundException`, **空回调把错误吞了** | 互操作调用一律回传结果; 空 catch 只允许出现在"上报自身"这类自保路径 |

**处置原则(已写进约定)**: 凡是可能失败的调用, 必须把失败回传成**调用方可判断**的结果; 写了降级路径就必须让失败可观测, 否则降级等于不存在。

## 二、静态门禁看不见的运行时约束

| 案例 | 现象 | 根因 | 现在怎么防 |
| --- | --- | --- | --- |
| 引导层/插件面板无效 | 不弹窗、按钮点了没反应 | 元素标记写在 `<script>` **之后**, app.js 同步执行时取不到 → 初始化 return | GHTML 新增"被 JS 取用的元素必须声明在 `app.js` 之前"(同时统计 `$('id')` 与 `getElementById('id')`) |
| 插件按钮插错作用域 | 加载即报 `d is not defined` | 代码插到 `plgCard` **外面**, 却引用了函数内的局部变量 | GBOOT 顶层加载断言(静态语法检查看不出, 运行门禁当场拦下) |
| 跨端参数名不对齐 | "显示命令行窗口"开关反着坏 | 前端发 `{show}`, 后端只读 `o.visible`(`undefined !== false` 恒真) | 契约断言(backend-flow)+ 前端改动一律配一条落盘/写回断言 |
| 按钮动作字符串不对齐 | "立即测试播报"永远报"未知测试类型" | 前端传 `regular`, 插件只认 `hour/special` | 已修 + 记入教训: 插件 call 的入参名字要有契约断言 |

## 三、"只读不写"的控件(改了等于没改)

- 识别方式(以及倒计时/显示/循环三个参数)只从 config **读**、没有任何写回路径; 显示(秒)甚至读错了键名(`eachMs` vs `displayMs`)。
- 用户唯一能察觉的时机是"重启之后", 所以这类 bug 通常会以"设置不保存"的形式被报告。
- **护栏**: `PROCESS-02 §0` 新增约定"读 config 的控件必须能写回 config"; backend-flow 增加落盘契约断言; G-BOOT 增加"改了必须发出保存请求"的接线断言。

## 四、同名不同物 / 名字误导

- **两个 `mode`**: 识别方式(`auto/vision/ocr`)与截图区域(`window/region/screen`)走不同接口, 移植时最容易被合并掉。
- **接口名 ≠ 接口职责**: `/api/ocrtl-vision` 实际是面板上唯一能写 `ocrtl` 的地方, 按名字找"mode 该发哪"自然找不到。
- **`hash` 的口径演进**: index.js → 整个目录 → 目录 + permissions, 三级并存; 记录里必须写清"哪一版起用哪个口径"。
- **护栏**: 语义写进开发者文档 + 授权哈希把"声明"也纳入被签名范围。

## 五、工具链与环境的坑(会直接写坏代码)

| 坑 | 症状 | 规避 |
| --- | --- | --- |
| 行尾追加 `//` 注释 | 注释吃掉同一行后面的语句(本会话踩过 3 次) | 单行代码不要追加行尾注释; 改完立刻 `node --check` |
| `String.replace` 的替换串 | `$&`/`$'` 被当特殊序列, 文件被写坏 | 用 `split/join` 或 JSON 承载片段 |
| PowerShell 未定义变量 | 求值为 `$null`, 类型转换后变 0/空串, **不报错** | 外部输入字段名在函数入口集中取一次; 靠"实跑一次"发现 |
| `windowsHide: true` | 子进程不再共享父控制台(拿不到父窗口句柄) | 需要共享控制台时显式 `windowsHide: false` |
| UNC 工作区 | npm/shell 把 cwd 折叠到 `C:\Windows`(npm audit 必然失败), robocopy 输出中文按 OEM 编码乱码 | npm 加 `--prefix`; 证据用"文件数差值"而不是按名字匹配 |
| 编辑器工具会剥 BOM | 含中文的 `.ps1` 丢 BOM → PS5.1 按 GBK 读 → 中文排除项静默失效 | 每次改完 `.ps1` 跑 G2; `make-dist` 有 0a 前置断言 |
| helper `.ps1` 的 ASCII 口径 | 新加中文注释立即被 G2 拦下 | 保持 helper 脚本注释英文(或用 BOM 口径, 但别两套混用) |
| 门禁脚本自身的判定口径 | `RunStep` 用 `$LASTEXITCODE` 判定, 纯 PS 步骤被误判 FAIL | 检查逻辑落成可执行脚本, 让退出码说话 |

## 六、进程常驻化带来的新纪律

- 常驻进程(截图助手)与一次性进程的差别: **资源泄漏会累积**(GDI+ 句柄、定时器、子进程), 失败也不会随进程退出而消失。
- 已加: 代次隔离(旧进程的 exit/数据不得影响新进程)、stdin error 监听、超时立即断开、写前校验进程存活、退出时收尾、try/finally 释放 GDI+ 对象。
- 教训: 常驻化的收益(省掉每次 ~0.5 秒冷启动)是真的, 但要连带处理"谁来收、死了怎么办、起不来怎么办"。

## 七、打包与出厂

- **黑名单式排除必然越用越漏**: 本会话一次性补了若干条, 根治办法是清单文件化(`scripts/pack-exclude.json`, make-dist 与 pack-audit 共用) + docs 白名单。
- **`.gitignore` 不是打包排除表**: robocopy 只认 `/XD /XF`; 被 git 忽略 ≠ 不会出厂。
- **测试夹具要在开发目录**: `plugins/conflict-test`(全权限)留在产品目录, 既会被复制进包, 又被审计规则当成"必备项"。
- **包必须与提交绑定**: 只按版本号找包, 迟早拿旧代码打的包去过审计; 现在包内 `BUILD-INFO.json` 的 commit 必须等于 HEAD。
- **C1 级机密的头号泄漏路径是开发脚本的临时目录**: 门禁自测曾把 `dev-dongle/master/master.key` 与真实 config 复制到 `%TEMP%` —— 凡复制整仓, 先过一遍"仓库里有什么机密"。

## 八、审计与门禁自身要复核

- **没人跑的门禁等于不存在**: `dep-audit` 的产物基线自 vendor 裁剪后就过期了, 发布审计第 4 步一直 FAIL —— 因为没人跑 `release-audit`。
- **"发布前那一遍"不能只当仪式**: 15 项常规门禁全绿的状态下, 发布审计仍查出两处真实漂移(新攻击面未进基线、扫描器把 CSS `z-index` 当端口)。
- **失败要留下痕迹**: release-audit 步骤里的 `exit 1` 会跳过报告写入, 已改为 `$script:exit = 1; return`。

## 九、本轮四条最值得记住的

1. **让失败可观测** —— 假成功是本轮所有严重问题的共同形状(截图/提示音/控制台/开关)。
2. **位置与顺序也是契约** —— HTML 里"标记在前、脚本在后"、插入代码要确认作用域, 这类约束静态检查看不出来, 要专门加门禁。
3. **"没人跑的门禁"和"被吞掉的错误"等价** —— 都让问题沉默地存活。
4. **照抄建议比不改更危险** —— 例如 `app.isPackaged` 在本项目的运行方式下恒为 false, 照抄会得到"看起来修了其实没变"; 审计建议要按实际运行方式复核后再落地。
