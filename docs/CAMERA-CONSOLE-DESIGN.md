## 1.5 第二轮反馈(2026-10-19 用户):横屏优先 + 导播台定位

**用途**: 协作 / 导播 —— 需要时让**另一个人当导播**, 或者必要时**远程网络控制**。
"需要额外人帮忙当导播的场景, 肯定是要搞大事情的时候了。"

**这一轮的要求(全部采纳)**:

| # | 要求 | 处理 |
| --- | --- | --- |
| 1 | **横屏优先** | 主设计按横屏做;竖屏作为降级形态(8 个垫) |
| 2 | 横屏**多出第二组打击垫功能区** | 第一组 = 预设运镜/常用动作;第二组 = 开关量 |
| 3 | 竖屏推子太挤 -> **推子通道可自定义编辑** | 增加"通道编辑"页, 用户自选哪些参数进推子 |
| 4 | **"发送"与"播放/暂停"竖着排列** | 右侧三个大圆钮**竖向**堆叠:发送 / 播放暂停 / 归中 |
| 5 | **不要叫 cue** | 改叫 **「发送」**(副标 LOAD) |
| 6 | 预设文件名后面加**紧急停止** | 加在顶栏;⭐ **长按 2 秒**防误触 |
| 7 | 文件名太长 -> **前后滚动** | 顶栏做**跑马灯** |
| 8 | **怎么展示运镜正在播放?**(时长很模糊) | 见下节 |
| 9 | **开关量放进打击垫, 数值量用推子** | 已按此重构(见下) |

### 1.5.1 「正在播放」怎么展示(用户的问题)

    ✅ 能做:  **播放状态灯** —— /dolly/Play 是可读的 T/F, 轮询即可知道"播/停"
    ✅ 能做:  **估算进度条** —— 播放开始时按"导入文件的时长"启动计时, 显示 已过/总长
    ⚠️ 只能估算: **运镜的真实播放进度读不到**(OSC 没有这个地址);
       而且**速度模式下文件里的时长不可信**(实测文件写 7 秒, 实际播了 363 秒)
    ⭐ 自动校正: 播放结束时 /dolly/Play 会回到 false -> 我们用这个时刻**校正**计时器
    => 呈现方式: 状态灯(确定) + 进度条(标注"估算") + 到时自动归零

### 1.5.2 打击垫与推子的分工(用户提出, 已采纳)

    **打击垫(开关量/一次性动作)**
      预设运镜 P1~P8 · 相机模式(4) · 图层(自己/他人/场景/UI/绿幕)
      开关类: 飞行 · 对准我 · 滚转水平 · 俯仰水平 · 防抖 · 联动镜头旋转
      动作类: 拍照 · 归中 · 复位
    **推子(连续数值)**
      飞行速度 · 转向速度 · 光圈 · 焦距(手动模式) · 曝光 · 变焦
      · 平滑强度 · 对准我偏移 X/Y · (运镜)时长

## 七点九、⭐ 核心设计原则:闭环反馈 + 多端同步(2026-10-22 用户)

**用户原话**:
> "我认为成品功能在使用时应当形成闭环反馈, 客户端和插件的操作变更应当同步。"

这是整个控制台的**核心要求**, 写进设计基线。

### 原则拆解

   ① **单一数据源**: 插件维护一份"相机状态缓存", 它是唯一真相;
   ② **双向同步**: 网页改了 -> 插件 -> VRChat;  其它途径(含用户手动在 VRChat 面板里改)变了 -> 插件 -> 网页;
   ③ **写后必读回**: 任何写入后都要读一次, **以读回值为准**并广播(应对"写 1 读回 15"那类怪癖);
   ④ **不可闭环项要坦白**: 没有 OSC 入口的值(跟随方式 / 对焦模式 / 对焦点)明确标"需手动设定", 不假装能同步。

### 技术架构(可实现, 全部基于已验证能力)

    [VRChat]
       ↑ OSC 写(127.0.0.1:9000)         ↓ OSCQuery HTTP 读(端口每次启动变, 从 output_log 取)
    [camera-path 插件]
       · 状态缓存(唯一真相)
       · 每 ~1 秒轮询 /usercamera 全部值 -> 有变化就更新缓存
       · 写入后 200~500ms 读回确认, 不一致则告警并广播读回值
       · WebSocket 服务(局域网, 需开启+口令) 把变化**推**给所有已连接客户端
    [控制台网页] × N
       · 连接 WebSocket -> 收到全量状态 -> 之后只收增量
       · 拖动推子: 本地立即跟手(手感) + 节流(约 100ms)发给插件 -> 插件写+读回 -> 广播校准
    => ⭐ **任意一端(网页 A / 网页 B / 插件 / VRChat 面板)改动, 所有端都会同步** ✓✓

### 验收方式(以后按这个测)

    · 网页 A 拖推子 -> 网页 B 与 VRChat 面板**都跟着变**;
    · 在 VRChat 面板里手动改光圈 -> 网页**自动刷新**到新值(证明读的是真值, 不是回显);
    · 断开一个网页再连上 -> **立刻拿到当前真实状态**(不是默认值);
    · 对没有 OSC 入口的项, 界面显示"需手动设定"而不是假装同步。

## 3. 推子清单(建议 9 个, 横向可分页)

    飞行(开关) · 飞行速度 · 转向速度 · 光圈 · 焦距 · 曝光 · 变焦 · 平滑 · 滚转水平

> 每个推子**: 上方数值 + 中间轨道 + 手柄 + 下方参数名**。
> ⚠️ 数值必须在**上方**(用户明确要求: 手会遮住推子下方的数字)。

## 4. 交互要点

    · **CUE** = 把选中的预设运镜"发送"到 VRChat(相当于 /dolly/Import)
    · **PLAY** = 播放/暂停(相当于 /dolly/Play|PlayDelayed 3)
    · 推子: **手指拖动**调值, 且**写后读回**(避免 VRChat 端出现怪值)
    · 手动控制/允许/锁定/复位: 控制"推子是否可动 / 是否被锁定 / 一键还原默认"
    · 手机友好: 大触控区(≥44px)、暗色、无滚动条、横向分页看推子

## 5. 待定的设计问题(需要用户拍板)

1. **推子数量**: 一屏 9 个偏挤 -> 是否改成"推子分页"(飞行页/镜头页/图层页)?
2. **手机方向**: 竖屏(推子多)vs 横屏(更像 DJ 台)? 建议**响应式**, 两种都给。
3. **打击垫功能组**: 4 组够不够? 是否要加"事件/自动化"组?
4. **紧急停止**: 是否加一个**全局大红按钮**(停止运镜 + 关相机 + 复位)?
5. **数值显示位置**: 竖屏放推子上方 ✓; 横屏可放推子旁边(空间更宽)。

## 6. 技术形态(初步)

    · 由 camera-path 插件**自带一个静态网页**(插件目录下), 主进程暴露只读/只写的最小接口;
    · 局域网访问: 监听 0.0.0.0 的独立端口(默认关闭, 需在插件设置里显式开启并给出口令);
    · 网页只调用**插件自己的 api**(不直连 OSC), 由插件统一做"写后读回确认";
    · 移动端: 纯原生 HTML/CSS/JS, 无框架、无构建, 便于长期维护。
