# F-20260929-02 输入法兼容性: 让候选窗/下拉在程序内可点(VR 桌面视图)

> 来源: 用户 2026-09-29 —— 「我想研究一下输入法兼容性, 有没有什么方法能让第三方输入法的选词框在程序里内嵌。因为 OVR 的选择窗口功能会显示整个窗口范围的画面, 但是操作只能操作选定显示的窗口, 浮在上面的输入法选词框没有办法点击, 我们软件的选择下拉菜单也是。我想如果直接内嵌在里面显示, 这样直接按虚拟键盘上的数字键选词比自己的内置输入法好用多了。」
> 状态: **D1 完成(设计已写, 等用户过目后进 D2)**。D0 见 §6, 四契约与切片见 §7。

## 1. 现象与机制(为什么点不着)
- OVR Toolkit / XSOverlay 的"选择窗口"模式:**画面**只抓一个窗口的矩形, **输入**也只发给那一个窗口;
- **输入法候选窗是独立顶层窗口**(系统/第三方输入法自己创建的) -> 它浮在被抓窗口之上, **画面能看见, 但点击事件进不去** ✗;
- **我们自己的 `<select>` 原生下拉**同理: 下拉弹出的是一个**独立窗口**(不是页面内容) -> 在 VR 里同样点不着 ✗(当前控制台里共 **15 处** `<select>`);
- 结论: 凡是"由操作系统/别的进程画出来的浮层", 在这个模式下都点不着; 想点得着, **必须画在我们自己的窗口里**。

## 2. 三条路线(按代价从低到高)

### 路线 1: 把 `<select>` 换成**页面内自绘下拉**  ⭐ 建议先做
- **做什么**: 用 HTML/CSS/JS 自绘下拉(按钮 + 列表 + 键盘/点击选择), 替换 15 处原生 `<select>`;
- **依据**: 页面内容由我们渲染 -> 天然在"被抓窗口"里 -> VR 里可点、键盘可选;
- **代价**: 低(纯前端, 一个通用组件);
- **收益**: 立刻解决"我们自己的下拉点不动", 且为后续(候选列表)提供现成的 UI 组件;
- **风险**: 低。

### 路线 2: 抓取系统输入法候选窗 + 自绘 + **回送数字键**  ⭐ 用户设想的形态
- **做什么**: ① 用 **UI Automation(UIA)** 读取输入法候选窗里的候选列表; ② 在我们的界面里画一份(与虚拟键盘同一层, 可点/可用数字键); ③ 用户点某一项时, 把**对应的数字键**送给输入法(输入法本来就支持数字选词) -> 完成选词;
- **依据**: 屏幕阅读器 **NVDA** 就是这么读 Windows 11 输入法界面的(UIA + AppModule, 见 nvaccess/nvda PR #14836) —— 说明"从外部读到候选文本"**有先例、可行**;
- **代价**: 需要一个**原生辅助进程**(UIA 在 C# 里很好写; 我们有现成的 csc 工具链与同类工具经验); 候选窗的 UI 结构在不同输入法/版本之间**有差异**, 需要逐个适配与降级;
- **风险**: 中 —— 取决于用户实际使用的输入法; **必须先做探针**(见 §4)再投入。

### 路线 3: TSF **UILess 模式**(官方正路, 但我们做不了)
- **做什么**: 应用实现 TSF 的文本存储 + 候选 UI 接口(`ITfCandidateListUIElement` 等), 由**应用自己画候选**;
- **依据**: 微软文档《UILess 模式概述》明确这是官方机制;
- **代价/风险**: 高 —— ① 需要完整的 TSF 宿主(工作量大); ② **输入法支持度不一**(微软拼音较配合, 第三方未必); ③ **我们的宿主是 Electron/Chromium**, IME 由 Chromium 自己管 -> 要接管等于改 Chromium;
- **结论**: 只在路线 2 被证伪时才考虑。

## 3. 与内置输入法的关系(用户原话: 数字键选词比内置的好用)
- 我们**已经有**内置拼音引擎(`/api/pinyin`, 6 万词库)与网页键盘;
- 但用户要的是**系统输入法**的候选(词库与学习更好) -> 两条路**不冲突**: 内置引擎继续做"不依赖系统输入法"的兜底, 路线 2 做"借系统输入法之力";
- 界面层可以**共用同一套候选条组件**(路线 1 顺手产出的那个)。

## 4. 建议的下一步: 一个 30 分钟的可行性探针(路线 2)
- **做什么**: 写一个小工具, 用 UIA **监听输入法候选窗**; 用户随便在某个输入框里打字, 工具打印它读到的候选项文本;
- **判定**: 能稳定读到候选 -> 路线 2 成立, 我们做"内嵌候选条 + 数字键回送"; 读不到 -> 退回路线 1(自绘下拉)+ 内置输入法, 放弃"借用系统输入法"这个想法;
- **顺带验证**: 我们合成的数字键能否被输入法接受(能否真的完成选词)。

- **范围**: **只解决桌面视图**(OVR 在 VR 里点击的仍然是运行在桌面的程序, 它只是把窗口投进来)。
- **候选数量**: **9 个**; **必须支持翻页**。
- **顺序(用户拍板)**: **先把"点不着的浮层"解决, 再研究借用系统输入法**。-> 本卡先做**路线 1**, 路线 2 留作后续独立立项。
- **流程要求**: 「按照标准流程来」-> 先 D1 四契约, 再 D2 切片。

## 7. D1 设计(路线 1: 页面内自绘下拉)

### 7.1 主体 vs 插件
**主体**(控制台前端)。理由: 它服务的是"**整个控制台在 VR 桌面视图里可用**"这条通用能力, 与某个具体插件无关。

### 7.2 四张契约
| 契约 | 本切片内容 |
| --- | --- |
| **API 契约** | **不新增任何端点**(纯前端组件) -> `docs/ROUTES-BASELINE.json` 保持 **73 条**不变 |
| **配置契约** | **不新增任何配置键**(下拉是纯 UI, 不进配置) |
| **显示契约** | 不适用(不产出公告板内容, 不占 144 字符预算, 不参与优先级阶梯) |
| **权限契约** | 不适用(不是插件, 无 manifest) |

### 7.3 门禁契约(本项目特有, 必须逐条满足)
| 门禁 | 要求 | 本设计如何满足 |
| --- | --- | --- |
| **GUWIRE** | 带 id 的 `button/input/select/textarea` 必须在 UI JS 里以**带引号字符串**出现 | 组件用 `<button id="X" data-value="...">`; 接线调用 `__dsel.mount('X', ...)` 自带引号字符串 |
| **GHTML** | JS 里 `$('id')` 的目标必须在 HTML 存在 | 同上(控件留在 HTML 里, 只换实现) |
| **html-inline-check(下拉显式 value)** | 读过 `.value` 的 `<select>` 每个 `<option>` 必须显式 `value=` | 我们**不再使用 `<select>`** -> 该规则自然不适用; **但组件必须自己保证"文案与取值分离"**: 值放 `data-value`, 文案可翻译(这条门禁背后的教训原样保留) |
| **GI18NH / GI18N / GI18NU** | 不许硬编码文案; 三语键对齐; 引用必须存在 | 组件文案一律 `data-t` / `tr()` |
| **GBOOT** | 前端启动可执行 | 组件在 `DOMContentLoaded` 前不碰 DOM; 初始化失败只降级不抛(不阻塞启动) |

### 7.4 组件契约(内部契约, 写进文件头 —— 照 theme.js / fx.js 的做法)
```
window.__dsel = {
  mount(id, opts),        // opts: { options:[{value,labelKey|label}], value, placeholderKey, width }
  get(id),                // 当前值(字符串) —— 取代原来的 $('id').value
  set(id, value),         // 程序设值(不发 onChange)
  onChange(id, fn),       // 用户选择后回调(fn(value, label))
  closeAll()
};
```
**行为契约**:
- 点击按钮 -> 展开候选列表(在按钮**下方**, 有 z-index, 不被卡片裁切);
- 点击某项 -> 选中 + 回调 + 关闭; 再次点击按钮/点击组件外部/Esc -> 关闭;
- **键盘**: ↑/↓ 移动高亮, Enter 选中, 数字 1~9 直接选第 N 项(**VR 虚拟键盘就靠这个**);
- 无障碍: `role="button"` + `aria-expanded` + `role="listbox"/"option"`;
- **降级**(兼容兜底): JS 出错时该控件退化为**普通文本**, 不显示成"可点却没反应"的样子。

### 7.5 D2 切片(每片独立、可单独回退; 每片都跑门禁 + 提交)
| 切片 | 内容 | 为什么这样切 |
| --- | --- | --- |
| **1** | 组件本身 + **1 处**转换(动作页的"动作文件"下拉) + 断言脚本 | 最小闭环: 组件与门禁都验到, 影响面最小 |
| **2** | 触发器 3 处 + 键盘页 1 处 | VR 里最常用的路径 |
| **3** | 翻译系统 4 处 | 文案/取值分离最容易出错的区域(正好验组件契约) |
| **4** | 其余(高级设置 / 数据源 / 环境检测等) | 收尾; 至此 `<select>` 归零 |

### 7.6 D3 断言(新增一个检查脚本, 注册进 run-gates.ps1)
1. `window.__dsel` 五个方法齐全;
2. `index.html` 里 **`<select>` 数量逐片下降**, 切片 4 后为 **0**;
3. 每个自定义下拉都有 `data-value`, 且**取的是值不是文案**(用组件 API 断言, 不读 DOM 文本);
4. 键盘行为: 数字键 1~9 选第 N 项、Esc 关闭、Enter 选中(在 frontend-boot 的 DOM 桩里断言);
5. **不回归**: GBOOT / GUWIRE / GHTML / GI18N 全绿(现有 15 门禁一条不红)。
