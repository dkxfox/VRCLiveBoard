# F-20260925-02 附件: VR 虚拟键盘技术研究(2026-09-25)

> 用户补充需求(2026-09-25): **给所有人用**; 自己的环境是 **PC 端 SteamVR + VD 串流**(OVR 类工具在 SteamVR 环境里自启动);
> **中文走系统安装的输入法**(搜狗/微软等, 要做好兼容 —— "微软输入法不兼容很多游戏, 所以我才装了搜狗");
> **只用于 VRChat 聊天框**; 另外希望**把输入法的语音输入能力接进来**, 方便"无言势"这类玩家。
> 本文件是研究记录(不随包出厂, docs/FEATURES 已在 pack-exclude); 结论请配合功能卡正文看。

## 1. 显示路径: 为什么"SteamVR overlay"是必选项

| 路线 | 谁在用 | 我们的可用性 |
| --- | --- | --- |
| **OpenVR `IVROverlay`(SteamVR 覆盖层)** | OVR Toolkit / XSOverlay / Desktop+ 等第三方覆盖层的**唯一成熟路径** | ✅ 首选。SteamVR 在跑就有效 —— **VD 串流的内容就是 SteamVR 合成后的画面**, 所以"PC 端 SteamVR + VD 串流"这套(你的环境)覆盖层**正常显示** |
| OpenXR `XR_EXTX_overlay` | 新标准, 生态成熟度与运行时覆盖都不如 OpenVR | ⚠️ 后续观察, 不作为首期 |
| 纯 VD OpenXR 运行时 / Quest Link / 独立机 | 不运行 SteamVR 就**没有**第三方覆盖层的位置 | ❌ 覆盖不到 → 必须有**降级方案**(见 §5) |

关键点:
- 覆盖层要"显示 + 能点", 走的是 OpenVR 的标准输入流: 创建 overlay → 设置纹理/尺寸 → 把控制器射线投影成 overlay 上的鼠标坐标 → 接收 `VREvent_MouseMove` / `VREvent_MouseButtonDown`(参考 dev.to 的 "SteamVR Overlay with Unity: Overlay Events" 与 Valve 官方 `openvr.h`; 最小 Python 例子见 openvr-overlay-bunny)。
- **随 SteamVR 自启动**是已有工具都在做的事(OVR Toolkit 的"随 SteamVR 启动"就是这么配的) —— 我们也可以在实现期按同样的方式注册(细节留到设计阶段核对 `steamvr.vrsettings` / 应用清单)。
- 已有先例证明"VR 里打字"这件事本身有人做成过(你给的 VRCTT 截图; 另外日文圈有 IwashiIME 这类 VR 输入法工具) —— **难点不在画键盘, 在输入法与候选窗**。

## 2. 输入法: 真正的坑在"候选窗", 不在按键

需求是"走系统输入法(搜狗/微软都行)"。这决定了架构: **必须让输入发生在一个真正的 Windows 窗口里**, 系统输入法才会工作。于是有三条实现路:

### 路线 A(推荐): 真窗口 + **自绘候选**(TSF 优先, IMM32 兜底)
- 输入框放在我们自己的窗口里(Electron 窗口即可, 它就是普通 Win32 窗口), 系统输入法正常喂字;
- 候选词**我们自己画**: 优先用 **TSF**(Win8+ 的输入法框架, 已取代 IMM)的 `ITfUIElementSink` / `ITfCandidateListUIElement` 拿组合串与候选列表, 画进覆盖层;
  老式只暴露 IMM32 的输入法退回 `ImmGetCandidateList` + `ImmSetCompositionWindow`。
- 为什么这条能解决你说的"微软输入法不兼容很多游戏": **微软拼音是现代 TSF 输入法**, 很多游戏只实现了 IMM32 那套 → 拿不到候选、只能盲打; 我们**同时实现两套**, 就不会卡在某一类输入法上。
- 现成参考: 阿里云那篇《TSF 自定义候选词列表界面》讲的就是"**触摸屏软键盘 + 自绘候选**"这个完全同构的需求(它的结论: 系统自带屏幕键盘满足不了, 必须自绘候选) ✓
- 代价: 需要一小段**原生代码**(TSF/IMM32 都要碰), 且要按输入法做兼容测试(搜狗 / 微软拼音 / QQ 拼音 / 手心 …)。

### 路线 B(最快): **区域截屏**把候选窗一起显示
- 不碰输入法 API, 直接把"输入框 + 候选窗所在屏幕区域"截进覆盖层(Desktop+ 的 region 捕获思路)。
- 优点: 任何输入法都能显示候选, 开发量最小。
- 缺点: 候选窗位置/多屏/DPI 缩放会影响取景(要动态跟随), 有闪烁, 观感差一档。**适合当作 A 的兜底开关**。

### 路线 C(退化): 只显示组合串, 不显示候选
- 有些输入法支持"候选嵌入输入框"(各家设置不同); 我们只显示输入框内容, 让用户在 VR 里"盲选"或用数字键选。
- 优点: 零输入法 API; 缺点: 体验差, 只作为最后的兼容模式。

**建议**: 先按 **A** 实现, 同时把 **B / C 做成可切换的兼容模式**(用户遇到某个输入法候选不显示时可以一键切)。

## 3. 语音输入: 三条路, 建议"先接系统 + 可配热键"

| 方案 | 做法 | 评价 |
| --- | --- | --- |
| **Win+H(Windows 听写)** | VR 里点"语音"按钮 → 我们把焦点放到输入框并**合成 Win+H** → 系统听写把文字落进输入框 | ✅ 零依赖、Win11 中文可用; ⚠️ Win10 支持有限, 需按系统版本给提示 |
| **输入法自带语音**(搜狗语音输入等) | 每家快捷键不同 → 做成"**可配置热键**", 用户在设置里填自己的(比如搜狗语音输入快捷键), 我们在 VR 里一键透传 | ✅ 与"走系统输入法"的思路一致; 需要用户配一次 |
| **自建 ASR**(本地 whisper.cpp / 云端) | 我们自己做"按住说话 → 上屏", 不依赖任何输入法 | 体验最好、最可控; 但引入模型/授权/体积, 成本最高 → 列为可选后期 |

对"无言势"玩家的实际价值: 语音输入 + 一键发送 = **不用键盘、不用出声给世界听**(VRChat 里只有聊天框文字、说话仍然静音) ✓ 正是这类玩家的刚需。

## 4. 与主体程序的接口(这一步已经通了)

- 主体已有 `POST /v1/chatbox`(`{text, priority, ttlMs}`, 与 /api/chatbox 同一处理器), 键盘/语音拿到文本后直接调它 → 聊天框(内部走 OSC `/chatbox/input`)。
- 因此: **键盘工具可以完全独立于主体开发/发布**, 主体零改动(最多加"短语/历史"的存取端点, 也可以放工具本地)。
- 144 字上限与主体一致; 键盘界面自带计数器即可。

## 5. "给所有人用"必须先定的两件事

1. **交付形态**:
   - **(a) 独立小工具**(推荐): 像 OVR Toolkit 那样单独发布(自己的 exe + 随 SteamVR 自启动), 与主体通过 HTTP 通信。好处: 主体体积不变、可独立更新、非 SteamVR 用户不受影响; 代价: 多一个下载/更新渠道。
   - **(b) 随主程序出厂**: 用户一次安装就有; 代价: 主包体积/签名/构建链变复杂, 且对"没装 SteamVR 的人"是死重量。
2. **非 SteamVR 用户的降级**: 覆盖层显示不了 → 至少保证"**键盘页面 + 系统输入法**"这条路可用(用户已有的桌面视图/手机/VD 桌面), 也就是功能卡的 P0; 并在文档里写清"哪些环境能用覆盖层"。

## 6. 修正后的分期建议

| 期 | 内容 | 说明 |
| --- | --- | --- |
| **P0** | 主体「VR 打字」页(大键盘 + 144 计数 + 短语 + 中英切换 + 语音按钮占位) | 零原生依赖; 今天就能用现有桌面视图验证"系统输入法顺不顺" |
| **P1** | **独立 SteamVR 覆盖层工具**: 显示我们的输入窗口 + 控制器射线当鼠标 + 路线 A 的自绘候选(TSF/IMM32) + Win+H/自定义语音热键 + 随 SteamVR 自启动 | 这是"给所有人用"的主体工程; 覆盖 SteamVR 环境(含 VD 串流) |
| **P2** | 兼容模式开关(B 截屏候选 / C 组合串)、短语与历史管理、手势(抬手才显示)、主题 | 按用户反馈排 |
| **P3(可选)** | 自建 ASR(本地 whisper) + "按住说话" | 若语音输入价值被验证 |
