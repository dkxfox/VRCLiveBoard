## 1. 显示路径: 为什么"SteamVR overlay"是必选项

| 路线 | 谁在用 | 我们的可用性 |
| --- | --- | --- |
| **OpenVR `IVROverlay`(SteamVR 覆盖层)** | OVR Toolkit / XSOverlay / Desktop+ 等第三方覆盖层的**唯一成熟路径** | ✅ 首选。SteamVR 在跑就有效 —— **VD 串流的内容就是 SteamVR 合成后的画面**, 所以"PC 端 SteamVR + VD 串流"这套(你的环境)覆盖层**正常显示** |
| OpenXR `XR_EXTX_overlay` | 新标准, 生态成熟度与运行时覆盖都不如 OpenVR | ⚠️ 后续观察, 不作为首期 |
| 纯 VD OpenXR 运行时 / Quest Link / 独立机 | 不运行 SteamVR 就**没有**第三方覆盖层的位置 | ❌ 覆盖不到 → 必须有**降级方案**(见 §5) |

关键点:
- 覆盖层要"显示 + 能点", 走的是 OpenVR 的标准输入流: 创建 overlay → 设置纹理/尺寸 → 把控制器射线投影成 overlay 上的鼠标坐标 → 接收 `VREvent_MouseMove` / `VREvent_MouseButtonDown`(参考 dev.to 的 "SteamVR Overlay with Unity: Overlay Events" 与 Valve 官方 `openvr.h`; 最小 Python 例子见 openvr-overlay-bunny)。
- **随 SteamVR 自启动**是已有工具都在做的事(OVR Toolkit 的"随 SteamVR 启动"就是这么配的) —— 我们也可以在实现期按同样的方式注册(细节留到设计阶段核对 `steamvr.vrsettings` / 应用清单)。
- 已有先例证明"VR 里打字"这件事本身有人做成过(你给的 VRCTT 截图; 另外日文圈有 IwashiIME 这类 VR 输入法工具) —— **难点不在画键盘, 在输入法与候选窗**。

## 2. 输入法: 真正的坑在"候选窗", 不在按键

需求是"走系统输入法(搜狗/微软都行)"。这决定了架构: **必须让输入发生在一个真正的 Windows 窗口里**, 系统输入法才会工作。于是有三条实现路:

### 路线 A(推荐): 真窗口 + **自绘候选**(TSF 优先, IMM32 兜底)
- 输入框放在我们自己的窗口里(Electron 窗口即可, 它就是普通 Win32 窗口), 系统输入法正常喂字;
- 候选词**我们自己画**: 优先用 **TSF**(Win8+ 的输入法框架, 已取代 IMM)的 `ITfUIElementSink` / `ITfCandidateListUIElement` 拿组合串与候选列表, 画进覆盖层;
  老式只暴露 IMM32 的输入法退回 `ImmGetCandidateList` + `ImmSetCompositionWindow`。
- 为什么这条能解决你说的"微软输入法不兼容很多游戏": **微软拼音是现代 TSF 输入法**, 很多游戏只实现了 IMM32 那套 → 拿不到候选、只能盲打; 我们**同时实现两套**, 就不会卡在某一类输入法上。
- 现成参考: 阿里云那篇《TSF 自定义候选词列表界面》讲的就是"**触摸屏软键盘 + 自绘候选**"这个完全同构的需求(它的结论: 系统自带屏幕键盘满足不了, 必须自绘候选) ✓
- 代价: 需要一小段**原生代码**(TSF/IMM32 都要碰), 且要按输入法做兼容测试(搜狗 / 微软拼音 / QQ 拼音 / 手心 …)。

### 路线 B(最快): **区域截屏**把候选窗一起显示
- 不碰输入法 API, 直接把"输入框 + 候选窗所在屏幕区域"截进覆盖层(Desktop+ 的 region 捕获思路)。
- 优点: 任何输入法都能显示候选, 开发量最小。
- 缺点: 候选窗位置/多屏/DPI 缩放会影响取景(要动态跟随), 有闪烁, 观感差一档。**适合当作 A 的兜底开关**。

### 路线 C(退化): 只显示组合串, 不显示候选
- 有些输入法支持"候选嵌入输入框"(各家设置不同); 我们只显示输入框内容, 让用户在 VR 里"盲选"或用数字键选。
- 优点: 零输入法 API; 缺点: 体验差, 只作为最后的兼容模式。

**建议**: 先按 **A** 实现, 同时把 **B / C 做成可切换的兼容模式**(用户遇到某个输入法候选不显示时可以一键切)。

## 3. 语音输入: 三条路, 建议"先接系统 + 可配热键"

| 方案 | 做法 | 评价 |
| --- | --- | --- |
| **Win+H(Windows 听写)** | VR 里点"语音"按钮 → 我们把焦点放到输入框并**合成 Win+H** → 系统听写把文字落进输入框 | ✅ 零依赖、Win11 中文可用; ⚠️ Win10 支持有限, 需按系统版本给提示 |
| **输入法自带语音**(搜狗语音输入等) | 每家快捷键不同 → 做成"**可配置热键**", 用户在设置里填自己的(比如搜狗语音输入快捷键), 我们在 VR 里一键透传 | ✅ 与"走系统输入法"的思路一致; 需要用户配一次 |
| **自建 ASR**(本地 whisper.cpp / 云端) | 我们自己做"按住说话 → 上屏", 不依赖任何输入法 | 体验最好、最可控; 但引入模型/授权/体积, 成本最高 → 列为可选后期 |

对"无言势"玩家的实际价值: 语音输入 + 一键发送 = **不用键盘、不用出声给世界听**(VRChat 里只有聊天框文字、说话仍然静音) ✓ 正是这类玩家的刚需。

## 3.5 复用现有 LiveTranslate 做语音输入?(2026-09-25 用户提问)

**结论: 可行, 而且是我们这边最省的一路 —— 但它是"对已有用户的复用", 不能当作"给所有人"的方案。**

事实(来自 `docs/LIVETRANSLATE.md` 与 `plugins/livetranslate.js`):
- LiveTranslate 是**第三方便携软件**(Python 3.12 + uv + **SenseVoice Small ASR** + LLM 翻译, **要 RTX CUDA**), 不是我们的代码;
- 我们的集成方式是**读它的转写文件**: `transcripts/livetrans_*_translation.txt`, 每 1.5 秒扫一次取最后 N 行 → 推聊天框(源优先级 40, 12 秒无更新自动让位); 另有 OCR 兜底(默认停用)。
- 也就是说 **ASR 已经在它里面跑完了**, 我们只是消费结果 —— 复用它几乎零成本。

要改成"语音输入"必须动三处(都很小):
1. **取原文, 不取译文**: 字幕用的是 `_translation.txt`(中文→英文), 语音输入必须读 **`_original.txt`**, 否则你说中文、聊天框出英文;
2. **输入设备要是麦克风**: 它的用途是"把别人的话变字幕", 通常接**回环/系统声音**; 语音输入必须听**麦克风**。**这一点文档里没记录, 需要实测确认它能不能选设备**(它的控制面板有 RMS/VAD 指示, 说明在某路音频上跑 VAD) —— 这是唯一的外部不确定性;
3. **模式不同**: 字幕是"长期把最新行推上去"; 语音输入应该是**按压式/开关式**(按住说话 → 松手/停顿后上屏), 并且**默认关闭**, 界面上明确显示"正在听"。

为什么不能作为"给所有人"的唯一方案: 它体积大、**要 RTX CUDA**、安装与更新都不受我们控制 → 我们无权把它塞进发布包。
所以"给所有人"要**分层**: ① 已有 LiveTranslate 的用户 → 一行开关复用(最省); ② 普通用户 → Win+H 系统听写 / 输入法自带语音(可配热键); ③ 想要更好体验 → 我们自己的小 ASR(whisper.cpp CPU 也能跑小模型) 或任意第三方听写工具(走我们已有的 `POST /v1/chatbox` 通用入口, 文档写清即可)。

## 4. 与主体程序的接口(这一步已经通了)

- 主体已有 `POST /v1/chatbox`(`{text, priority, ttlMs}`, 与 /api/chatbox 同一处理器), 键盘/语音拿到文本后直接调它 → 聊天框(内部走 OSC `/chatbox/input`)。
- 因此: **键盘工具可以完全独立于主体开发/发布**, 主体零改动(最多加"短语/历史"的存取端点, 也可以放工具本地)。
- 144 字上限与主体一致; 键盘界面自带计数器即可。

## 5. "给所有人用"必须先定的两件事

1. **交付形态**:
   - **(a) 独立小工具**(推荐): 像 OVR Toolkit 那样单独发布(自己的 exe + 随 SteamVR 自启动), 与主体通过 HTTP 通信。好处: 主体体积不变、可独立更新、非 SteamVR 用户不受影响; 代价: 多一个下载/更新渠道。
   - **(b) 随主程序出厂**: 用户一次安装就有; 代价: 主包体积/签名/构建链变复杂, 且对"没装 SteamVR 的人"是死重量。
2. **非 SteamVR 用户的降级**: 覆盖层显示不了 → 至少保证"**键盘页面 + 系统输入法**"这条路可用(用户已有的桌面视图/手机/VD 桌面), 也就是功能卡的 P0; 并在文档里写清"哪些环境能用覆盖层"。

## 8. 用户反馈与新增思路(2026-09-27 夜, 用户否掉"手机当键盘")

### 8.1 手机方案: **否决**(用户实机经验, 记下来别再提)
- 用户原话要点: ① 大部分 VR 头显是**沉浸式**的, 老旧头显**甚至没有彩色透视**; ② 即使有彩色透视, **透过摄像头的画面很模糊、不好操作**(用户自己试过); ③ 拿手机操作会**打断沉浸感**; ④ "不如手柄射线键盘"。
- 结论: **手机 / 透视路线不进入方案** —— 它解决的是"覆盖范围", 但代价是体验与沉浸感, 而这两条正是本功能存在的理由。
- 教训: 覆盖范围要靠**分层降级**去补(见 8.3), 不能靠牺牲主路径体验去换。

### 8.2 新证据(本地实测): VRChat **会回传**控制器 / 语音信号 —— 可以零原生代码做"触发器"
- 来源: 用户机器上的 VRChat OSC 头像配置(%USERPROFILE%\AppData\LocalLow\VRChat\VRChat\OSC\usr_*\Avatars\avtr_*.json, 取最新一份, 2026-09-21 生成): **202 个参数全部带 output 地址**。
- 实测存在且**会被发出来**的内置参数: Voice(语音键状态) · GestureLeft / GestureRight(手柄手势 0~7) · GestureLeftWeight / GestureRightWeight · MuteSelf(是否静音) · Seated · Grounded · VRMode · AFK · Viseme · Earmuffs · VelocityX · InStation。
- 注意区分方向(极易搞错): /input/*(如 /input/Jump)是**我们 → VRChat**(官方《OSC as Input Controller》), **不能**拿它当"读手柄按键"; /avatar/parameters/* 的 **output** 才是 **VRChat → 我们**(端口 9001)。
- **由此得到一条此前没有的路**: 用**手柄手势 / 语音键 / 静音状态**当"一键说话 / 发送 / 取消"的**触发器** —— **零覆盖层、零原生代码、任何头显都能用**(Quest 独立机也行, 因为它不依赖覆盖层)。
- 前提与代价(诚实): ① 游戏内要开 OSC(本项目用户本来就开着); ② 我们要新增一个 **UDP 9001 监听**(目前只发不收), 若 9001 被别的 OSC 工具占用会冲突 → 端口可改 + 占用提示; ③ 手势在不同控制器上映射不同(Index 无手势键、手势锁定等) → **触发器必须可配置 + 可多选**(手势 / 语音键 / 桌面热键), 并给一次"学一遍"的引导。

### 8.3 把"输入"拆成两层: **触发层** 与 **识别层**(回应"不想用 LiveTranslate 的玩家怎么办")
- **触发层**(什么时候开始 / 结束输入): 手柄手势 · Voice 语音键 · 桌面全局热键 · 覆盖层按钮 · 我们键盘页上的"按住说话"。**统一走一套 PTT 状态机**, 与识别方式无关。
- **识别层**(把声音变文字)四选一, 按"零安装优先"排:
  1. **Windows 系统听写(WinRT SpeechRecognizer)** —— 离线、免费、不装任何第三方软件; 我们**已有 WinRT 常驻 PowerShell 助手的成熟先例**(SMTC 媒体信息就是这么做的), 复用同一条链路即可; 需要系统中文语音包(通常已有), 精度中等但"说一句上屏"够用;
  2. **自建小 ASR(Vosk, Apache-2.0, npm 包 + 中文小模型约 40MB, CPU 流式)** —— 端到端我们自己的, 延迟低; **模型分发要单独解决**(对端网络可能不通 GitHub / HuggingFace → 评估走 npm 镜像, 或让用户手动放模型);
  3. **whisper.cpp / faster-whisper(本地)** —— 精度最好、体积最大, 后置选项;
  4. **复用 LiveTranslate 的转写文件**(读 _original.txt, **不是译文**) —— 最省, 给已装它的用户;
  - 外挂通道: **任何第三方听写工具**都能直接调我们已有的 POST /v1/chatbox(文档写清即可, 零开发)。
- 这样一来: 用户想用哪个识别引擎都行, **触发器与界面都不用变**; 不想装 LiveTranslate 的玩家有 1 / 2 两条零安装或轻安装的路。

### 8.4 与"射线键盘"配套的结论: 中文候选**自绘**比走系统输入法更值得
- 用户明确"手柄射线键盘"是首选形态, 而射线打字的瓶颈是**中文选词**(不是按键速度), 于是:
  - 走系统输入法 → 必须解决候选窗在覆盖层里的显示(TSF / IMM32 自绘或区域截屏, 见 §2), **每个输入法都要兼容测试**;
  - 走**自带拼音候选(纯 JS 词库 + 自绘候选 / 翻页 / 简拼 / 常用词学习)** → 不碰任何输入法 API, **所有人体验一致**, 候选 UI 可以直接按"能用射线点"设计(候选按钮大, 一排 5~7 个 + 翻页)。
- 建议: **射线键盘以自绘拼音候选为主路径**; 系统输入法 + 区域截屏保留为"我就想用搜狗"的兼容模式(与 §2 路线 A/B 不冲突, 只是默认值反过来)。

### 8.5 原待确认项的状态更新
- ~~LiveTranslate 的音频输入能不能选麦克风~~ → **已查实: 能**。其 user_settings.json 里同时有 audio_device(回环, 当前 null)与 **mic_device: "__default__"**, audio_capture.py 里有 list_input_devices() / _mic_device_name → 复用方案成立(仍要改成读 _original.txt + 按压式 + 默认关)。
- 交付形态(独立工具 / 随包): 仍待拍板 —— 若先做"键盘页 + 自绘拼音 + 触发器", 两者都不需要原生代码, 这个问题可以推迟到原生覆盖层真正开工时再定。

## 9. 可行性确认(2026-09-27 夜, 用户要求「搞一下资料确认可行性」)

### 9.1 用户要求拆解(原话)
> 「我的 VR 是 quest3, 当然我们也要给 Index 做兼容, 所以得有个选项让用户自己选; 识别层也得两个都有, 有用户不安装 LiveTranslate 也得能用; 射线键盘我们得有个方便的触发方法, 所以把这些功能的触发手势做成能自定义怎么样?」
→ 四件事: ① 设备可选(Quest 3 为主 + Index 兼容); ② 识别层两条都要; ③ 射线键盘要有方便触发; ④ **触发手势可自定义**。

### 9.2 触发器侧: **可行**, 而且推荐做成「学习式自定义绑定」(结论)
- 证据(本地 + 官方文档): 用户当前头像的 OSC 配置有 **202 个参数全部带 output**(107 Bool / 75 Float / 20 Int); 其中**内置可当触发器**的有 `Voice`、`GestureLeft`、`GestureRight`、`GestureLeftWeight`、`GestureRightWeight`、`MuteSelf`、`AFK`、`Seated`、`VRMode`、`Grounded`、`Viseme`、`Earmuffs`、`InStation`; 且 VRChat 载入头像时会发 `/avatar/change`(带头像 id) —— 我们能据此**定位该头像的 OSC 配置文件并列出「哪些参数会发出来」**。
- **为什么不硬编码设备**: 与其为 Quest / Index / 手势追踪各写一套映射(还要赌它们在游戏内的按键定义), 不如让用户**教我们一次** ——
  「学习」按钮 → 用户在 VR 里做那个动作(握拳 / 按语音键 / 自定义头像开关) → 我们监听 9001, 把**真的发生变化**的参数列出来(过滤 VelocityX 这类每帧都变的高频浮点噪声) → 用户选一个, 绑成「开始说话 / 发送 / 取消」。
  · 好处: 任何头显、任何控制器、任何头像都能用(只要那个信号会被 VRChat 发出来); Index 兼容 = 用同一套流程在 Index 上跑一遍即可, **我们不需要预先知道 Index 的手势映射**。
  · 预设(Quest / Index / 手势追踪)只是省一步的便利 —— **预设可以错, 学习模式不会错**, 这就是「给所有人用」的兜底。
- 延迟: VRChat 的参数是「变化时发」, 走本机 UDP。预期「按下 → 开始听」在 50ms 内, **待实机实测**(见 9.6)。
- 端口风险: VRChat 的 OSC **输出口固定是 9001**(游戏内改不了) —— 本项目当前不监听它(实测现在空闲); 若用户装了别的 OSC 工具(VRCTextboxOSC 等)会抢占 → 必须**检测 + 明确提示**, 不能静默失效。
- 工程面: 主体新增一个 UDP 9001 监听 + 参数变化事件流(无新依赖, 已有 `osc` 包), 再把事件接进 PTT 状态机。

### 9.3 识别层两条路: **都可行**
- **① 不装 LiveTranslate(零安装)= Windows 系统听写**: 本机已验证 —— WinRT `SpeechRecognizer` 类型可用 ✓, `SupportedTopicLanguages` 含 **zh-Hans-CN** ✓, 用 zh-Hans-CN 能**成功创建识别器** ✓, `ContinuousRecognitionSession` 可用 ✓, 麦克风隐私对桌面应用为 **Allow** ✓。做法: 常驻 PowerShell 助手(与 SMTC 媒体信息同一模式)输出 JSON lines → 主体。**待实机测**: 中文连续听写的精度与断句(要对着麦克风念两句)。
  · 注意: 系统听写是**分段出结果**, 不是逐字流式 —— 对「说一句 → 上屏」够用; 若精度不满意再上自建 ASR。
- **② 复用 LiveTranslate(最快)**: 已查实它能选麦克风(`mic_device`)✓; 改动只有三处: 读 `_original.txt`(原文, 不是译文) · 按压/开关式 · 默认关 + 界面明示「正在听」。约半天。
- **③ 自建 ASR(后期可选)**: npm `vosk` 是 Apache-2.0 ✓ 但**解包 85.9MB** ✗, 且中文模型要另行下载(alphacephei / HuggingFace 在对端网络可能不通 ✗)→ 定为「插件按需下载 + 允许用户手动指定模型路径」的后期项, 风险已明确。

### 9.4 射线键盘的自绘拼音候选: **可行, 授权干净**

## 10. 首次实机数据: Quest 3 采集 60 秒(2026-09-28 上午, 用户实机)

- 采集方式: 双击 `scripts/dev/osc-monitor.bat`(等价 `--learn --seconds 60 --json auto`); 数据落在 `logs/osc-<时间戳>.json`。
- 总量: **60.0 秒 / 5647 条 / 12 个地址**。

**① `Voice` 不是 Bool, 是 0~1 的浮点(麦克风电平)**
- 32.72s 起连续 173 次变化(0.008 → 0.267 → 回落), 同时 `Viseme` 在 32.74~34.72s 变化 16 次(说话时的口型)→ **它是「正在说话」的实时电平, 不是按键状态**。
- 设计影响: 可以据此做**「说话即听写」(VAD 式, 不用按键)** —— 阈值(如 > 0.02)+ 静音 400ms 收尾; 但**不能**当成干净的「按住」信号。

**② 手势 0~7 是干净的数字信号, Quest 3 手柄完全可用 ✓**
- `GestureRight` 50 次变化: 出现过 **1(握拳)/2(张开)/3(食指指)/4(胜利)/5/6(手炮)/7(点赞)/0(中性)**; `GestureLeft` 14 次(0/2/4)。
- `GestureLeftWeight` / `GestureRightWeight` 是**渐变权重**(0 → 0.07 → 0.47 → 0.90 → 1, 每档约 10~30ms)→ 说明手柄手势是「按键触发 + 权重渐变」, 权重可用来做「按到一半不触发」的防抖。

**③ `MuteSelf` / `AFK` 是干净 Bool**: MuteSelf 5 次(true/false 切换)、AFK 4 次。

**④ 延迟(心跳法)**: 用消息最多的 `Upright`(5244 条, 中位 **10ms** ≈ 87Hz)当心跳, 内置参数每次变化距「前一次心跳」**中位 9~14ms、最大 28~45ms** → **VRChat 从状态变化到发出 OSC 约在一帧内(≈10ms)**, 对「握拳开始说话」完全够用(感知不到)。

**⑤ 高频噪声清单(学习模式会自动过滤)**: `Upright` 是最大噪声源(10ms 一条); 头像自定义的 `GestureTail` / `GestureWing` / `GestureAhoge`(~1.1 秒一次)是**动画参数**, 也该默认排除(它们不是输入)。

**⑥ `/avatar/change` 本次没出现**(进游戏之后才开始采集)→ 想顺带看头像配置, 要**先启动监听再进游戏**。

**Quest 3 预设(据实测)**: `开始说话` = `GestureRight == 1`(握拳)或 `GestureLeft == 1`; `发送/结束` = 手势回到 `0`; `暂停听写` = `MuteSelf == true`; 备选**说话即听写** = `Voice > 0.02`(静音 400ms 收尾)。**Index 仍走「学习模式 + Voice/热键兜底」**(本地无 Index 可测)。

**工具修正**: 第一次采集被第二次**覆盖**了(文件名原先是固定的)→ 现在 `--json auto` 生成带时间戳的 `logs/osc-<YYYYMMDD-HHMMSS>.json`; 并新增 `--analyze <文件>` 事后分析(含延迟上限估算), Index 志愿者/其它用户可以只把文件发回来。

## 11. 静音行为实测(2026-09-28, 两轮各 45 秒): **静音会抑制 Voice, 但不影响手势**

- 数据(时间戳文件名, 两轮都在): `osc-20260928-104347.json` 45.1s/5432 条 · `osc-20260928-104542.json` 45.0s/5228 条。
- **`Voice`(麦克风电平)**: 非静音期间 **808 / 689** 次(峰值 0.67 / 0.63), **静音期间 0 次(峰值 0.0000)** —— 两轮完全一致(静音时长 15.8s / 17.2s; 用户按引导在静音时确实说了话)。
- **手势不受静音影响 ✓**(用第一轮 60 秒那份数据按静音窗口切分): 静音期间 `GestureRight` **23** 次、`GestureRightWeight` 5 次、`GestureLeft` **7** 次、`GestureLeftWeight` 2 次、`AFK` 2 次 —— **静音状态下手势照常上报**。
- 顺带: `Viseme`(口型)静音期间也是 **0 次** → 说明**静音时 VRChat 根本不处理麦克风**(不只是"不上报 Voice")。
- **新增噪声**: `AngularY`(中位 16~21ms)与 `Upright` 同级, 一起进默认过滤名单。
- **对预设的决定**:
  - **主触发器 = 手势**(右手握拳 = 开始说, 松开回 0 = 发送)—— 静音也能用 ✓;
  - 「说话即听写」(`Voice` 电平) **只对不静音玩家有效** → 仍然做, 但界面必须写明"静音时不工作", 并在 `MuteSelf == true` 时提示"静音中, 请用握拳";
  - **重要澄清**: 静音只影响 **VRChat 自己**的上报与发送, **我们自己抓麦克风做 ASR 不受影响** → 静音玩家用「握拳 + 本地 ASR(系统听写 / Vosk / LiveTranslate 选麦克风)」可以**完整走通** ✓; 唯一不成立的是"静音时靠 VRChat 的 Voice 电平自动触发"。

| 官方注释(前几节已引) | `MakeOverlaysInteractiveIfVisible` = 「system-wide laser mouse mode … whenever this overlay is visible」 | **不能常开**(否则抢输入 = AFK); 改成**只在射线打中键盘时**临时开, 离开就关 |

### 12.9 D1 设计: 切片「自算射线 + 抓取/放置」(路线 A 的第 2 刀)

**目标**: 射线由我们自己算 → 面板上有真实靶点与高亮; 扣扳机**抓起**键盘、松手**钉在当地**(R1/R2); 平时**不抢游戏输入**(R4)。

| 契约 | 内容 |
| --- | --- |
| **输入读取** | `IVRSystem`(经 `VR_GetGenericInterface("IVRSystem_026")`): ① `GetTrackedDeviceIndexForControllerRole`(18) 取左右手; ② `GetDeviceToAbsoluteTrackingPose`(12) 取姿态(HMD 0 号 + 两手); ③ `GetControllerState`(37) 读扳机(`ulButtonPressed` 第 33 位 / `rAxis[0].x` 模拟量)。全程 **legacy API**, 自带、不需要 action manifest |
| **射线** | 起点 = 手柄位置(姿态矩阵第 4 列); 方向 = 手柄**朝前** = 姿态矩阵第三列取负(**-Z**)。成熟工具用的是 action 系统的 **aim 姿态**; legacy 只有 grip 姿态, 先用 -Z, 若实测偏了再补一个**可调偏置**(记在 D2 备注里) |
| **求交** | 面板平面由我们自己的 overlay 变换确定(位置 + 法线已知) → 射线与平面求交 → 换成面板局部 UV → 复用现有 `Hit()` 命中测试 |
| **抓取/放置** | 扳机按下且射线打中面板 → **抓取态**(键盘跟手移动, 保持竖直/只跟偏航, 免得歪成一片); 松手 → 写回 `SetOverlayTransformAbsolute` **钉住**。抓取期间扳机不再当作点键 |
| **不抢输入** | **默认不开** `MakeOverlaysInteractiveIfVisible`; 仅当"键盘已显示 **且** 手/射线指向键盘"时临时打开(让系统激光鼠标替我们**吃掉**那一发扳机, 免得游戏里误触), 一旦指开立刻关闭。这样"游戏不能操作"的坑不会再出现 |
| **显示** | 靶点/高亮改由**自算射线**驱动(不再依赖系统鼠标事件的坐标 —— 实测它恒为 (0,0)) |
| **失败降级** | 拿不到 `IVRSystem` / 手柄未连接 / 姿态无效 → 该只手不参与, 面板保持可看不可点, 日志写明原因; 抓取态下与 SteamVR 断开 → 立即钉在当前位姿(不会跟着飞到天上去) |

**D3 断言(不需要 VR 也能跑, 这是本切片最大的好处)**: 给 tool 加 `--sim` 模式, 用**假姿态 + 假扳机**喂进去, 断言:
1. 射线对准某个键 → 命中的键正确(与 `Hit()` 单测互相印证);
2. 边沿检测: 按住不放只产生一次"按下", 松开一次"松开";
3. 抓取: 按下+移动 → 面板位置跟着变; 松开 → 位置固定(再移动手柄面板不动);
4. 指开面板 → 不开交互(不抢输入);
5. 断连/姿态无效 → 抓取态下原地钉住。

**这一刀之后的形态**: 键盘可以拿起来放、松手悬浮、射线点键、中文候选(引擎已就绪) —— 即用户描述的最终效果。
