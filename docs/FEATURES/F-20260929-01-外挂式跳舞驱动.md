## 1. 技术可行性: 能做与不能做(先说清楚, 免得白做)

### 1.1 **能做的**: 我们当"PC 端播放器"
- VRChat 的模型动作由**模型自带的 Animator + 动画片段**播放, **参数**决定"放哪一段、放到第几秒";
- 外挂程序能做的正是**驱动这些参数**:
  · **时间轴同步**: 每帧把"当前进度"(归一化 0~1 的 float)发给 `/avatar/parameters/<Float>` -> 模型里的接收端按它播放(**这就是各类 dance sync 的工作原理**);
  · **选曲/触发**: 发 `/avatar/parameters/<Int>` 或内置的 **`VRCEmote`**(int 1~8) -> 切歌 / 触发内置舞蹈;
  · 我们现在**已经有**这套发送能力(动作输出层, 已交付并测过)。

### 1.2 **不能做的**(必须提前讲明)
- ❌ **不能把任意 MMD 动作"注进"别人的模型**: VRChat 的动画片段必须**烘焙在模型里**, 运行时无法外部注入 -> 所以「**模型里完全不装任何东西就能跳任意 MMD**」做不到;
- ✅ 但「**不用装第三方 PC 端工具**」做得到: 模型里只需一个**接收参数并播放**的简单 prefab(很多免费/开源方案提供), **PC 端那个难用/收费的播放器由我们替代**;
- ✅ 另一种**纯外挂**情形: 模型里本来就是**固定几支舞**(用 `VRCEmote` 或自定义 int 选曲), 那我们连接收端都不用改, 直接发参数即可。

### 1.3 一个关键精度事实(决定体验)
- VRChat 的 **Expression Parameter** 同步时**每个参数最多 8 bit**(来源: proustite「Float Expression Parameters 同期の概念」: 「パラメータごとに最大 8bit を使用して同期」) -> 远端看到的进度是 **256 级**;
- 而 **OSC 本地设置不受这个限制** -> **本人看到的是平滑的**, 旁人看到的是量化的;
- 对我们的意义: 播放器可以放心地按 **30~60Hz** 发 float, 本地体验由我们的平滑度决定; 远端同步质量取决于模型参数位深(这一点要在功能说明里如实写)。

### 2.1 ⚠️ 一条会导致法律问题的红线
**绝大多数 MMD 动作禁止"MMD 以外用途"、明确禁止 VRChat、禁止再配布。** 因此:
- ✅ **我们的插件绝不能内置/附带任何动作文件**;
- ✅ 正确架构: **插件只做"播放器 + 参数发送"**, 动作文件由**用户自备**(他自己确认过许可的 VMD/FBX);
- ✅ 插件里可以放**示例配置与说明**(怎么把自己的动作挂进来), 但不放素材本身。

## 6. **路线 B(用户提出, 已查证: 可行且是标准做法)**: 虚拟追踪器 —— 绕开"动画必须烘焙进模型"的限制

> 用户原话: 「我有个想法哈, 我用过动作捕捉设备, rebocap 这种, 我把动作搞成类似动捕设备, 或者预设动作这样……不就能绕开限制了?」
> **结论: 对, 而且这正是动捕设备(Rebocap / SlimeVR / Mocopi)在 VRChat 里工作的原理。**

### 6.1 机制(有据可查)
- VRChat 的模型姿势由**全身 IK** 从**追踪点**(头 / 双手 / 腰胯 / 双脚, 以及可选的胸、膝、肘)解算出来 —— **不需要模型里烘焙任何动画**;
- 因此只要让 SteamVR **看见虚拟追踪器**, VRChat 就会把模型摆成对应姿势;
- 现成的开源驱动: **Virtual Motion Tracker(VMT, gpsnmeajp)** —— 官方说明原文:
  > 「An easy-to-use **virtual tracker driver for OpenVR**. … You can send **pose (position and rotation) with OSC Protocol** and use it as a **virtual tracker on SteamVR**.」
  · **许可证: MIT** ✓(可以放心依赖/分发说明, 无 GPL 污染);
  · **v0.14 起支持 Skeletal Input**(可做手套型控制器 -> **手指**也能喂);
  · 有 API 文档与示例代码(官方文档站)。
- 与路线 A 的关键差别: **路线 A**(发 `/avatar/parameters/*`)要求模型里**有动画片段 + 接收端**(用户模型"什么都没有" -> 走不通);**路线 B** 只要求用户装一次 **VMT**, **模型侧零改动**。

### 6.2 我们这边要做的活(**零原生代码**)
1. 读动作(VMD; 或我们自己的预设动作) -> 取**骨骼关键帧**;
2. 把骨骼映射成**追踪点姿态**(头 / 胸 / 腰 / 左右手 / 肘 / 膝 / 脚, 按可用数量);
3. 以 30~60Hz 通过 **OSC 发给 VMT**(沿用动作输出层已有的速率上限/断流归零等安全约束);
4. 播放控制(开始/暂停/停止/循环/跳转) + 与触发器层联动(手势开始/停止)。

### 6.3 诚实说清限制(别指望"像素级还原 MMD")
- VRChat 的 IK 是**近似**解算: 走路 / 挥手 / 转体这类**大动作**跟得上;
- **脊柱与腰胯的扭转、地面接触、脚步滑动**会有"面条感"和滑步(这是所有虚拟追踪器方案的固有现象, 不是我们的 bug);
- **手指**要另走 Skeletal Input(VMT 0.14+ 支持)才能驱动, 否则手指仍由手柄输入决定;
- 所以观感是「**一个人跟着这支舞在跳**」, 而不是"完美复刻"。这一点必须先说清楚, 免得预期错位。

### 6.4 新增的待确认项
- 用户是否接受**为了这个功能装一次 VMT**(MIT, 免费, 小驱动)? —— 这也是所有动捕设备/Rebocap 走的同一条路;
- 追踪点数量期望(决定 IK 观感): 3 点(头+双手) / 6 点 / 11 点(加胸·膝·肘);
- 是否需要 Skeletal Input(手指)。
