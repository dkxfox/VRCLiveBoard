## 1. 七问(D0)

1. **谁在什么场景下用**:
   开 VRChat 直播的人。**收到醒目留言/上舰/礼物时, 镜头自动做一段运镜**(推到公告板前 / 环绕 / 切预设机位), 弹幕刷屏时切无人机视角。

   相机 OSC 端点不存在 / 用户没有 VRC+ → **静默降级**: 不再发相机报文, 插件卡上显示"相机 OSC 不可用", 其余直播功能(弹幕/礼物进聊天框)**完全不受影响**;

## 7. ✅ 切片 0 进展:运镜导出格式已破解(2026-10-14)

用户导出样本位置: `C:\Users\10166\Documents\VRChat\CameraPaths`(用户文档下)

### 7.1 文件与两种坐标模式

```
VRChat_CameraPath_Local_2026-10-14_11-00-04.json   6937 字节  13 个关键帧
VRChat_CameraPath_World_2026-10-14_11-03-58.json   3710 字节   7 个关键帧
```
- 命名: `VRChat_CameraPath_{Local|World}_<日期>_<时分秒>.json`;
- **Local = 跟随玩家位置**(局部坐标), **World = 世界坐标** —— 正好对应你说的"跟随玩家位置"与"世界坐标"两种;
- 顶层是 **JSON 数组**, 每个元素是一个关键帧。**格式是纯文本 JSON, 完全可以解析** -> 需求③(导入导出)与需求④(轨迹查看)**技术可行**。

### 7.2 关键帧字段(实测 18 个, 全部为数值)

| 字段 | 样例值 | 含义 |
| --- | --- | --- |
| `IsLocal` | true/false | 局部(跟随玩家)/ 世界坐标 |
| `Position` | {X,Y,Z} | 位置 |
| `Rotation` | {X,Y,Z} | **欧拉角(度)**, 注意值接近 360 表示 0 附近(样本里 Z 恒为 359.0232) |
| `FocalDistance` / `Aperture` | 2 / 15 | 对焦距离 / 光圈 |
| `Hue` / `Saturation` / `Lightness` | 120 / 100 / 50 | 滤镜 HSL |
| `LookAtMeXOffset` / `YOffset` | 0 / 0 | "对准我"偏移(⭐ 与已确认的 OSC 地址同名) |
| `Zoom` | 20 ~ 90.95 | 变焦(焦距) |
| `Exposure` | 0 ~ 3.017 | 曝光 |
| `Speed` | 0.4 ~ 1.0 | ⭐ 速度(对应"速度模式") |
| `Duration` | 2 | ⭐ 时长(对应"时间模式") |
| `Index` | 0..4 | 在**本段路径**内的点位序号 |
| `PathIndex` | 0..3 | ⭐ **路径段序号** —— 一个文件可含**多段路径** |

### 7.3 由此确认/新增的判断

1. ✅ **手册里"路径管理:可顺序播放多个动画"得到证实** —— `PathIndex` 就是分段(样本 13 个点分布在 4 段里);
2. ✅ **运镜不只是移动**: 每个点位同时带**镜头参数**(变焦/曝光/滤镜/对焦), 所以"轨迹"= 运动 + 外观;

## 8. ✅ 已定:时间模式与速度模式的字段判定(对照样本, 2026-10-14)

用户做了**同一条路(总位移 6.68)的两条运镜**作为对照:

| 文件 | 模式 | 关键帧 | Speed | Duration | 结论 |
| --- | --- | --- | --- | --- | --- |
| ...11-15-50.json | **速度模式** | 2(末点) | **0.978** | 2(默认) | **Speed 携带设置** |
| ...11-16-22.json | **时间模式** | 2(末点) | 0.4(默认) | **7.057** | **Duration 携带设置** |

**判定规则(实现依据)**: 每个关键帧上,
- `Duration != 默认值` -> 该段是**时间模式**, 值 = **A 到 B 的秒数**(可精确计算总时长);
- `Speed != 默认值` -> 该段是**速度模式**, 值 = 速度系数(0.4 是默认);
- 两者都是默认值 -> 该段无位移(单点路径), 忽略。

## 9. ⭐ 用户亲述的编辑器行为与真正的痛点(设计的靶心)

**编辑器怎么工作**: 摆好镜头位置 -> 点"添加"(记录当前参数) -> 与上一个镜头位置**按设置里的拟合方式做加减速计算** -> 确定轨迹。

**痛点(用户原话)**:
> "速度模式下你控制运镜的速度实际上**不是你在游戏里移动镜头的速度**, 运镜的速度要慢得多。
> 也就是**不是所见即所得**, 需要编辑好了后点一次播放看一下运动效果。
> 所以**大部分时间用时间模式**比较好控制, 因为它的移动时间就是 A 到 B 的时间。"

**这直接给出了本功能的价值主张**:
```
时间模式  -> Duration 已知 -> **我们可以精确算出这段运镜要多久**(进游戏前就知道)
速度模式  -> Speed 是系数, **导出文件里没有最终时长** -> 只能进游戏播放才知道 -> 这就是痛点
```
-> 因此"轨迹查看"(需求④)**不是锦上添花**, 而是**解决痛点的核心**:
   画出 A->B 的走向 + 每段时长/速度曲线 + **给出预计总时长**, 让用户**不必进游戏播放就能判断**。

**为此需要一份标定数据(下一批验证)**:
请用户播一次**速度模式**那条(6.68 位移 / Speed 0.978)并**计时**,
再由若干组"位移-速度-实测时长"拟合出时长估算(拟合方式未知, 只能实测反推)。

截图 UI 显示"下行速度 3.0", 而文件里 Speed 的取值范围是 **0.4 ~ 1.0** -> 两者**不是同一量纲**。

### 14.2 由此定案的三件事

1. ⚠️ **§13.2 的假设被推翻**: 两条文件里都写着 `Duration = 7.057`, 而实际是 **363 秒 / 26.9 秒**
   -> **速度模式下文件里的 Duration 不是播放时长**(是设置里遗留的值) -> 「预计时长」**不能读 Duration, 只能标定**;

3. ⭐ **时间模式仍然可精确算**: `Duration` 在时间模式下等于 A->B 的秒数(用户口述 + 7.057 样本)。

### 14.3 标定协议(为用户时间着想, 用短距离)

### 14.4 实现结论(可直接进 D1)

- **时间模式**: 解析 `Duration` 求和即得总时长(精确);
