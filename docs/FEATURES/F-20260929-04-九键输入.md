# F-20260929-04 九键(手机 T9)输入

> 来源: 用户 2026-09-29 —— 「这个输入法支持移动设备上的那种九键输入吗?」
> 状态: **路线 A 已交付**(2026-09-29): 数字索引 28,733 个数字串 + 九宫格 + 键盘切换选项; 整句留待路线 C。

## 1. 现状: **不支持**
当前键盘是 **26 键全拼**: 每个字母一个按钮, 拼音串直接查词库(键 = 完整拼音)。九键要的是完全另一套映射:
```
2 abc   3 def   4 ghi   5 jkl   6 mno   7 pqrs   8 tuv   9 wxyz
```
用户按的是**数字串**(例如 `64` 可能是 ni / mi / oh …), 需要把数字串映射到候选词。

## 2. 为什么在 VR 里值得做(用户直觉是对的)
- 九键**按钮更大、数量更少**(9 个 vs 26 个) -> 在 VR 里点中的难度下降一个量级;
- 这和本项目已确认的三条 VR 约束同源: 视野有限、目标要大好点、相关操作要挨在一起。

## 3. 三条可选实现路线
| 路线 | 做法 | 代价 | 效果 |
| --- | --- | --- | --- |
| **A. 词库 T9 索引(推荐起步)** | 启动时把词库建成 `数字串 -> [词]` 索引(与现有拼音键同源, 60k 词量级) | 小(一个切片) | 词组级候选: `64` -> 你/泥/拟…(按词频); **没有整句** |
| **B. A + 音节展开** | 数字串先展开成合法音节组合, 再喂给现有 DAG/HMM | 中(展开会组合爆炸, 需要限制) | 部分整句能力 |
| **C. 数字级 Viterbi** | 像手机输入法那样直接在数字串上做语言模型解码 | 大(要新增一套解码器与概率表) | 与全拼同级的整句能力 |

## 4. 建议
1. 先做 **A**: 它能让九键"能用"(词组级), 而且**复用现有词库与候选条**, 不引入新依赖;
2. UI 上作为键盘页的**模式切换**(26 键 / 九键), 与"候选数量"设置放在一起;
3. 若上手后觉得"想要整句", 再评估 C(那是另一个量级的工作)。

## 5. 待用户确认(D0)
1. 要不要做九键?(先做 A)
2. 九键版式: 标准手机布局(1 无字母、2-9 字母、* 符号、0 空格、# 切换)还是只放 2-9 的九宫格?
3. 是否保留 26 键(建议保留, 两者可切换)?

## 固化(2026-09-29, 用户决定)
- 用户结论: 「可以, 够用了, **固化这个模块**。一个**凑合用的、不带联网的输入法**而已, 没必要做成头部产品那种。」
- **冻结**: 本模块不再加功能。以下内容**明确不做**(都是有意留下的边界, 不是待办):
  · 联想/下一个词;
  · 九键的整句(路线 C, 数字级 Viterbi);
  · **任何联网能力**(云候选、云词库、统计上报) —— 这是**设计约束**: 输入内容只在**本机内存**里过一遍, 不出本机;
  · 皮肤/主题、候选排序的精细调参、词频手调。
- **维护约定**: 以后再动这一块(`src/pinyin.js`、`src/pinyin-userdict.js`、键盘页前端), 收尾前必须跑:
  ```
  node scripts/dev/ime-assert.js     # 12 条功能回归(整句/模糊音/简拼/长串耗时)
  node scripts/dev/ime-stress.js     # 五组压力测试(p95<=150ms, 最慢<=500ms)
  ```
- 用户词库(`logs/pinyin-user-dict.json`)与学习记录(`logs/pinyin-learn.json`)都**只在本机**, 不入库、不随包分发。
