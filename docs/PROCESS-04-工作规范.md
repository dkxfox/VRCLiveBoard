# 流程 4:工作规范(行动纪律 · 12 条)

> 配套:`docs/PROCESS-01-维护与优化.md`(维护流程)、`docs/PROCESS-02-开发更新.md`(开发流程)、`docs/PROCESS-03-安全审计.md`(审计流程)、`docs/GLOSSARY.md`(术语)。
> 定位:**前三份流程管"交付路径"(做什么、按什么顺序、过哪些门), 本文件管"动作纪律"(怎么调查、怎么改、什么时候停)。**
> 冲突时的优先级:**安全规范(PROCESS-03) > 本文件 > 具体流程里的操作细节**; 本文件不改变任何既有硬约束(五条硬约束、门禁、授权口径)。
> 这 12 条是为了治三个具体毛病: **看到线索就开冲 / 扩大假设 / 连续打补丁**。落地口径四句话:
> **先判别-最小测试; 失败两次刹车; 证据落盘; review 后 stop。**

## 0. 一页速查(最常看的其实是这一节)

**动手前(预检门)必须能回答 5 问**
1. 现象是什么? 复现步骤是什么?(复现不了 → 先只读调查, 不改代码)
2. 我的假设是什么? **什么结果会推翻它**?
3. 最小的验证动作是什么?(一条命令 / 一个断言 / 一个只读脚本)
4. 打算改哪些文件? 能不能只改一处?
5. 做完怎么知道对了?(可执行断言, 而不是"看起来好了")

**排查中**
- 至少列 2~3 个**互斥**假设, 先做**一次能排除最多假设**的测试;
- 只取"会改变做法"的证据(判决性优先);
- 同一现象**连续两次尝试无效 → 停**, 回到假设清单并汇报;
- "改完更糟" → **先回滚**到已知良好状态再分析。

**收尾(缺一不算完成)**
- 改动 + **证据** + **记录**(DEV-NOTES 条目 / ISSUES 卡 / 文档同步)三件套;
- 工作区干净、门禁绿、无凭据落盘、一次性脚本已删;
- 汇报固定结构: 结论 → 证据 → 变更清单 → 未决与风险 → 下一步(带推荐);
- **review 后 stop**: 用户没确认之前, 不开新的工作面。

## 1. 沟通规范

- **目的**: 每次交互都能被快速理解, 不产生"信息不对齐"造成的返工。
- **动作**
  1. 只问"能改变决策"的问题, 一轮不超过 3 个, 每个都给**默认答案 + 推荐**(用户可以直接说"按你说的");
  2. 汇报用**结论 → 证据 → 下一步**三段, 不铺垫、不寒暄;
  3. 不确定就写"**未验证 / 不确定**", 禁止用"应该/大概/可能"包装成结论;
  4. 术语与 `docs/GLOSSARY.md` 对齐, 同一件事只有一个叫法;
  5. 给选项必须写明**代价**(选 A 会怎样、选 B 会怎样), 不把技术选型猜谜丢给用户。
- **反例**: 只回"已完成"(不说完成了什么); 把猜测写成事实; 一次抛十个问题; 让用户在"A/B"之间凭感觉选。
- **判定**: 用户能仅凭汇报判断"能不能用、要不要继续"; 全文没有把不确定写成确定。
- **对应机制**: PROCESS-01 §2 A0 歧义闸(唯一映射不成立就回述确认); 本文件 §13/§0 速查。

## 2. 预检门(pre-check gate)

- **目的**: 动手前先确认"值得动手", 治"看到线索就开冲"。
- **动作**
  1. 任何非平凡改动前, 回答 §0 的 5 问; 任一答不上 → 只做**只读调查**(看代码/日志/文档), 不改代码;
  2. 现象**必须先复现**(或明确指出"无法复现, 只有一次日志");
  3. 假设必须配一个**证伪方法**; 写不出证伪方法 = 这不是假设, 是猜想;
  4. 明确**验收断言**: 用什么命令/断言证明修好了。
- **反例**: 没复现就改代码; 靠"应该就是这里"下刀; 一次改 5 个文件去试; 修完没有验证方法。
- **判定**: 改动前说得出证伪条件, 改动后指得出证明它的那条命令/断言。
- **对应机制**: PROCESS-02 §1 七问; ISSUES"先登记再动手、没有复现步骤标 NEED-REPRO"。

## 3. 证据与置信度

- **目的**: 把"我看到的现象"和"我认为的原因"分开, 结论必须带等级。
- **动作**
  1. 每条结论标注等级: **E1 实测可复现**(有命令/日志/截图) / **E2 代码或数据可查**(有文件行号) / **E3 第三方文档或成熟实现**(有链接) / **E4 推断**(必须写明"推断"并给出证伪方法);
  2. **E3/E4 不得当定论**; 交付前 E4 要么升级成 E1/E2, 要么在汇报里列为风险;
  3. 证据**落盘**: 命令、关键输出、结论写进 DEV-NOTES / ISSUES / 代码注释, 会话里的结论不算数;
  4. 引用外部资料要带链接与"我是怎么读的"(原文 vs 二手转述)。
- **反例**: 拿 E4 写进文档当结论; 汇报里不说"我验证过什么"; 只给结论不给出处。
- **判定**: 每个"已修/已确认"都能指向一条命令、一行代码或一个链接。
- **对应机制**: DEV-NOTES 六段模板里的"诚实记录"; ISSUES"根因(禁止'可能'), 修完必须写验证方式"; PROCESS-03 的发现项分级(C1-C4)。

## 4. 竞争假设

- **目的**: 治"第一个想法就是答案"。
- **动作**
  1. 现象出现时, 至少列 **2~3 个互斥假设**, 每个配"最便宜的判别方法";
  2. 先做**能一次排除最多假设**的那个测试(见 §5);
  3. 假设被全部排除 → 说明"现象描述或环境认知有误", 回到 §2 重新描述现象, **不要**在原假设上继续加补丁;
  4. 结案时给出"为什么其它假设不成立"的一句话。
- **反例**: 只写一个"根因"; 排除一个假设就宣布结案; 修完没好转还在同一假设上加码。
- **判定**: 排查记录里能看到假设列表与各自的判别结果(排除法也算)。
- **对应机制**: ISSUES 的"根因禁止'可能'"; 本文件 §9 失败制动。

## 5. 证据价值

- **目的**: 把时间花在"能改变决策"的观察上。
- **动作**
  1. 取证据前先问: **"这个结果会让我改变做法吗?"** 不会 → 不做;
  2. 优先级: ①能直接复现/证伪现象的 > ②能区分两个竞争假设的 > ③能暴露边界的(极端输入/空值/超长) > ④只是"更详细"的;
  3. 一次**判决性**证据, 胜过多条互相印证的软证据;
  4. 已经排除的假设不再重复验证(把结论写下来, 不要靠记忆)。
- **反例**: 反复打印同一个日志; 为"完整性"跑全量套件却不看结果; 收集一堆不改结论的数据。
- **判定**: 汇报里每轮都能说清"这条证据改变了哪个决定"。
- **对应机制**: 本文件 §11 预算; 门禁"一次跑全套"的约定(不重复跑无新证据的套件)。

## 6. 最小变更

- **目的**: 降低回归面与审查成本, 治"顺手重构"。
- **动作**
  1. 一次只解决**一个现象**;
  2. 优先改**一处**(单文件/单函数); 能加参数就不改签名, 能加分支就不改结构;
  3. **禁止顺手重构**: 要重构另立一轮, 且先有断言兜底;
  4. 改动 >3 个文件或 >150 行 → 先说明"为什么必须这么大", 并拆成**可独立回滚**的提交;
  5. "顺手清理"必须与本轮结论无关、且零行为变化, 否则不做。
- **反例**: 修 A 时顺便改 B 的命名/格式; 一个提交混两个不相关修复; 为了"更优雅"重写整个模块。
- **判定**: 每个提交能单独 revert, 且不带走无关改动。
- **对应机制**: PROCESS-02 §3 切片交付(每 commit 可独立 revert); PROCESS-01 §5 改动规模分档与可回滚硬指标。

## 7. 实验隔离

- **目的**: 任何实验都不能碰用户正在用的东西, 也不能污染唯一可信的环境。
- **动作**
  1. **绝不碰**用户实例(19190)与用户数据(`config.json`、`logs/` 原文); 一律用隔离副本 + 独立端口(1925x/1926x);
  2. 实验前记录**起点状态**(git status / HEAD / 关键配置), 实验后恢复;
  3. 有真实副作用的实验(外呼、发 OSC、写盘、装插件、改注册表)必须先落在隔离环境, 或显式征得同意;
  4. 实验产物写临时目录, 不留在工作区; 确需保留的 → 进 `scripts/pack-exclude.json` 并在汇报里说明;
  5. 隔离环境也要"干净": 例如把隔离实例的 OSC 出口指到没人监听的端口, 免得测试文本跑到用户眼前。
- **反例**: 在用户实例上试接口; 直接改用户 `config.json`; 测试时把 OSC 打到用户的 VRChat。
- **判定**: 每轮结束时 `git status` 干净、用户配置与日志未被修改。
- **对应机制**: `smoke.ps1` / `release-audit.ps1` 的隔离纪律(端口语义、VRCB_NO_SHELL、OSC 出口隔离)。

## 8. 行动闭环、持久化与工具经济

- **目的**: 每件事都有出口, 并且不重复造工具。
- **动作**
  1. **闭合三件套**: 改动 + 证据 + 记录(DEV-NOTES 条目 / ISSUES 卡 / 文档同步), 缺一不算完成;
  2. **一切落盘**: 结论写进仓库(文档/注释/测试), 不留在会话里 —— 验收标准是"**下次开工只读仓库就能接着干**";
  3. 提交前自查: 工作区干净、门禁绿、凭据不落盘、一次性脚本已删;
  4. **工具经济**: 先找现成脚本/门禁/夹具, 新增工具前先说明"为什么现有工具不行"; 复用 > 新写;
  5. 命令也要算成本: 能不联网就不联网, 能本地就不远程, 能只跑相关门禁就不跑全量(除非有新证据)。
- **反例**: 改完了没记录; 方案只存在于会话里; 每次都现写一次性脚本且不删; 为一件小事新造一套工具链。
- **判定**: 下次会话只读仓库即可继续; 仓库里没有"来历不明的脚本"。
- **对应机制**: DEV-NOTES 六段模板; ISSUES 卡; commit + push 纪律; `pack-exclude.json` 单一来源。

## 9. 失败制动

- **目的**: 治"连续打补丁"式浪费。
- **动作**
  1. **同一现象连续两次尝试无效 → 立即停止改动**, 回到 §4 重列假设并汇报(这就是"失败两次刹车");
  2. 同一轮里同一文件被"再修一次"累计两次 → 停下重述现象, 检查是不是假设错了;
  3. 出现"改完更糟" → **先回滚**到上一个已知良好状态(commit/stash)再分析, 不在被污染的树上继续;
  4. 制动时必须输出: 现状、已排除的假设、下一步的两条候选路径(含代价), 让用户选;
  5. 制动不等于放弃: 已排除的假设就是产出, 写进记录。
- **反例**: 第 3 次还在同一假设上加补丁; 不回滚就叠加修复; 悄悄继续不汇报。
- **判定**: 触发制动后, 汇报里明确出现"已停 / 已排除 / 请选路径"。
- **对应机制**: 本文件 §4 与 §11; git 提交粒度(便于回滚)。

## 10. 范围控制

- **目的**: 不让"顺手"把一轮工作撑爆。
- **动作**
  1. 每轮开工先写**本轮不做什么**(显式非目标);
  2. 发现新问题 → **登记(ISSUES)不顺手修**, 除非它**阻断**当前验收;
  3. 用户新需求先判断"同一现象"还是"新功能": 新功能走功能卡(七问)再排期, 不混进当前轮;
  4. 一轮结束不留"半成品状态": 要么完成, 要么回滚, 不留悬空 TODO。
- **反例**: 顺手修了个不相干的 bug; 一轮里塞进三个功能; 留下"改了一半"的接口。
- **判定**: 汇报能对上"开工时声明的范围"; 超范围的部分有独立登记。
- **对应机制**: PROCESS-02 §1 七问第 7 问"**不做什么**"; ISSUES 先登记再动手。

## 11. 停止、预算与输出

- **目的**: 明确"什么时候停""花多少""交什么", 避免无限打磨。
- **动作**
  1. **默认预算(可按需说明后放宽)**: 单轮代码改动 ≤3 个文件 / ≤150 行; 一次排查 ≤3 轮实验; 全量门禁 ≤1 次/轮(除有新证据);
  2. **停止条件**(满足其一即停并汇报): 达成验收断言 / 触发失败制动 / 触及预算 / **需要用户决策** / 需要外部条件(凭据、真机、用户确认);
  3. **输出结构**(固定): 结论 → 证据 → 变更清单 → 未决与风险 → 下一步(带推荐);
  4. **review 后 stop**: 用户 review(或明确说继续)之前, 不开新工作面;
  5. 触顶时不要"硬撑": 说明还差什么、下一步要什么, 比硬做完更有价值。
- **反例**: 明明需要用户拍板却自己拍; 预算耗尽还硬撑; 汇报没有"未决项"; 用户还没看就开下一个工作面。
- **判定**: 汇报结构固定且含未决项; 超预算有说明与用户确认。
- **对应机制**: PROCESS-01 §8 会话开场与收尾清单; 本文件 §0 速查。

## 12. UI 验证交接

- **目的**: UI/交互类改动 AI 无法自证, 交接必须清楚且不反复返工。
- **动作**
  1. **AI 侧先做能做的**: 门禁断言(GHTML / GUWIRE / GBOOT)、隔离实例端到端、静态可判定项(控件存在性/接线/文案键)、以及**一份可照做的验证步骤**;
  2. **交接必须写四件事**: ①要验证什么(逐条可判定) ②怎么触发(路径 + 前置条件) ③期望看到什么 ④不符合时把什么发回来(日志关键字 / 截图位置 / 报错原文);
  3. **一次交接只带一个待验证批次**(尽量一屏能验完), 用户确认后再改 —— 避免"改一轮就让用户重测一遍全部功能";
  4. 用户反馈回来先**复述现象 + 列假设**(§3/§4), 再动手; 不要把"用户说不行"直接翻译成"改这里"。
- **反例**: "你试试看"(没说试什么、看什么); 每次都要用户重测全功能; 收到反馈立刻改代码。
- **判定**: 用户能照着清单一次验完; 反馈回来能直接定位到改动点。
- **对应机制**: PROCESS-02 D3 验收四层(第 ④ 层"用户在自己实例上确认"为 UI 类必填); ISSUES"验证方式"; 门禁里的接线/启动断言。
